通过手机对机器人执行更新

状态：已发布，尚未在板卡实测 · 日期：2026-08-19 · 负责人：pierre

蓝牙更新链路大部分逻辑早已就绪，但从未有人完整走通。btd 已经可以转发更新相关的子集指令；updaterd 可以向请求方推送更新进度；duck-btctl 可通过调用接口访问全部能力。完整联调过程中发现一处严重缺陷：App 的标准流程（启动更新、查看进度）会出现机器人静默不执行更新；另外还有两处 updaterd 的小缺陷，同时整理了客户端接口设计要点。

本文记录发现的问题与最终决策。相关机制说明见配套文档：app-path-design.md §3.5 描述连接通道，§3.1 描述可转发指令子集；btd/src/route.rs 包含每条路由的设计考量。

1. 原有可用能力，无需重构

可转发指令子集包含查询与触发类接口：hello、update.check、update.apply、update.status、update.subscribe、update.log、update.listInstalled 均可送达 updaterd；robot.health 送达 robotd。本次没有新增协议方法。

apply 本身就会推送进度。updaterd 的 run_mutating 会在回复返回前，向本次 apply 请求对应的连接写入 update.progress 通知；btd 将上游每一行数据原样转发至会话，不解析内容；duck-btctl 打印不带ID的输出并持续等待。 也就是说，执行 apply 时无需额外订阅，BLE客户端就能收到进度。而 duck-btctl.md 文档之前描述相反：“在独立连接上执行 apply，全程静默直到完成”，该文档现已修正。

更新中途客户端断连重连不会丢失状态。updaterd 保存每个组件最新进度，新订阅者接入时会重放；update.status 在更新过程中基于缓存快照返回结果，并补入实时阶段信息。这两点正是手机端链路断开后重连所必需的。

并且回复会在通信通道断开前发出。updaterd 和 btd 是更新流程中不会被重启的两个服务；两者会在回复发出约5秒后重启（restart-order.md §1）。

2. 发现的问题

2.1 长耗时调用阻塞整个会话 · btd · 已修复

连接池策略：每个会话内，每项服务仅保留一条连接；后端两个守护进程在单条连接上串行处理请求。 如果先执行 update.subscribe，再执行 update.apply，apply 请求会写入一条已经不再被进度流读取的socket流：更新不会执行、不返回应答、也不抛出错误。用户点击“更新”，机器人毫无动作，且找不到任何报错。 先 update.apply 再 update.status 会触发同个缺陷，但症状更轻：机器人正常更新，状态查询却超时。

现在调用会按占用连接时长分组，每组独立通道。app-path-design.md §3.5 描述通道划分、部分场景复用单连接的合理性，以及否决“每个调用单独一条连接”的原因。两个故障场景均增加对应测试用例，无修复则测试失败。

这是本次改动里唯一无法在手机App侧规避的问题。

2.2 进度推送流量过大，而BLE通道仅20字节 · updaterd · 已修复

下载源会上报每一段HTTP分片（一个发布包会产生数千条消息），所有订阅方都会接收全部消息。单条进度文本约100字节，按btd的20字节帧长要拆成5~6条通知。客户端处理不及时时，btd 会丢弃报文，手机端看到的百分比随机跳跃，例如 12 → 61 → 34。

修改后：每完整1%最多推送1条通知，每秒最多4条，在生成进度数据的引擎内做消息合并；robotctl update watch 也会收到同样的流。被合并跳过的百分比会在下载结束时统一推送，避免高速下载卡在97%这类视觉异常。

2.3 update.check 会锁住引擎锁造成阻塞 · updaterd · 已修复

ipc.rs 文件头部定义规则：只读请求使用 try_lock，保证更新期间 status、subscribe 仍可响应。但 check 没有遵守该规则。 在执行 apply 期间调用它，会等到更新完成才返回，延迟可达数分钟。手机端视角看起来如同机器人失联。 现已改为立刻返回 BUSY；update.pin 同样修改。

2.4 决策：手机端支持版本回滚

update.rollback（回滚）与 update.select（选择版本）原本禁止转发，现在开放路由。update.pin、update.resetToGolden 保持禁止。 理由写在 btd/src/route.rs 路由定义，摘要见 app-path-design.md §3.1： update.apply 早已开放，是三者中风险最高的操作：从网络安装从未在本板卡运行过的代码。而 rollback 和 select 只是切回本机之前运行过的版本，无需下载，同样会经过健康门限校验与自动回滚。 引擎自带的自动回滚只处理健康校验失败的版本。但用户拿手机操作的场景往往是：新版本安装成功、通过健康校验，但后续表现变差——例如行走策略步态不稳、无线模块反复断连。这类场景引擎不会自动回滚，只能人工干预，而操作人员此时只有手机，无法SSH登录。

同时开放两个接口，而不是只开放rollback：因为 update.listInstalled 已经开放，App可以展示板卡全部版本列表。能展示却不能选择版本，功能残缺。select 需要从列表选中版本，存在误触选错版本的风险，这是接受的代价。

pin（版本锁定）是拒绝开放的重点：选错select版本，还能切回上一版，机器人会上报当前版本；一旦误触锁定版本，机器人会拒绝后续所有更新，并且报告自身已是最新版本——这种故障表现和正常状态几乎无法区分。

2.5 手机触发的更新日志都记为 btd · 记录备案，不做修复

updaterd 在每次变更操作时，通过 SO_PEERCRED 记录调用方UID与PID，用于售后排查“是谁触发了这次回滚”。 BLE链路下，所有手机的调用方都显示为 btd。btd 原样转发参数；如果新增调用者标识字段，btd 就不再是单纯管道，而变成请求发起方。 除非售后需要区分多台手机，否则暂不改动。

2.6 客户端超时是静默超时，不是固定总时长 · duck-btctl · 已修复

固定总时长超时存在弊端：要么中断正在正常运行的更新，要么无限等待宕机机器人。 而进度通知本身就是机器人存活的信号。现在超时判定改为静默超时：更新操作静默超时阈值3分钟，对应合法场景里最长的空闲间隔（安装后钩子脚本），不是整个更新允许的总耗时。手机App复用该设计思想，不直接复用代码。

2.7 守护进程apply应答发出约5秒后，蓝牙链路断开

不属于缺陷，是§1定义的正常重启顺序。但所有客户端都必须预期该现象；机器人主动断开连接不能判定为更新失败。客户端遵循如下时序：

  1. update.apply 返回执行结果，代表本次更新任务已完成。
  2. 大约5秒后 btd 重启，蓝牙连接断开。
  3. 客户端重连，调用 update.status。last_attempt 字段携带执行结果，就算第一步应答丢失，客户端仍可获取结果。 duck-btctl 会提前打印第二步断开提示。

2.8 保留：蓝牙支持 from_dir 参数（有意开放）

ApplyOptions.from_dir 指定机器人本地目录，对手机端无意义，仅调试台使用。 过滤该参数意味着 route.rs 需要解析参数而不只是判断方法名，而 btd 的设计原则就是不解析参数。前置校验已经拦截危险场景并给出提示，因此保留该参数。在此记录，避免后人误以为是遗漏。

3. duck-btctl 当前能力

支持 version；update 子命令包含 check, apply, status, versions, log, rollback, select, watch。命令名与 robotctl update 保持一致，在机器人本地学会的命令可以直接通过蓝牙使用。 参数基于 duck_ipc_proto 原生类型构建，而非手写JSON（旧call接口是手写JSON）。update.apply 的目标参数是外部标记枚举，--ref 和 --version 对应不同JSON结构，格式错误直接触发解析错误，无歧义。全部命令见 duckctl.md。

进度输出：每个事件单独一行打印到stderr，这是文档原先承诺、但旧版工具未实现的行为。

duck-btctl 属于临时过渡工具，这点很关键：§2.1、§2.2、§2.3是机器人侧修复，App可以直接受益；§2.6的超时策略属于客户端逻辑，工具已经实现，App需要单独记录该逻辑。

  • apply应答能否在btd重启前送达客户端

5. 明确不实现的功能

  • 无取消更新接口：更新引擎本身不支持取消，半完成的更新比缓慢更新更危险。客户端退出无需处理，更新会继续跑完。
  • 手机端无自动启用apply开关：deploy/updater.toml 刻意不将客户端机器人设为无人值守自动重启。在大规模集群评估完成前，不对外暴露该开关。
  • 不做加密：app-path-design.md §8.1负责加密相关设计，本次工作不受加密状态影响。文中所有关于无线范围内接入方权限的描述，前提都是加密功能暂未开启。

术语注释

  • BLE：蓝牙低功耗
  • daemon：守护进程
  • IPC：进程间通信
  • try_lock：非阻塞锁
  • SO_PEERCRED：套接字获取对端进程凭证
  • rollback：版本回滚
  • apply：执行更新
  • health gate：健康校验门限
  • stopgap：临时过渡方案
