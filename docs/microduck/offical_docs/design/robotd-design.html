robotd — 控制环路

状态：草案 · 日期：2026-08-20 · 负责人：pierre

本方案实现 architecture.md 第1节中 robotd 模块，覆盖 roadmap.md 的 M3 阶段。待迁移的原型工程为 apirrone/microduck_runtime，文档内统一称为 runtime（运行时）。

仅保留 alpha 版本硬件方案：仅 Radxa 主板、仅 v2 版 imu_to_dxl 板卡。废弃 v1/v1.5/v1.6 版本、其余4款IMU、3路摄像头以及树莓派。所有发布策略模型均为 alpha_* 系列。轮式构型保留为一个参数开关：policy.mode = "roller"（§4.2）；该配置仅选择一套策略与调参预设，并非独立硬件变体。

1. 整体架构

单进程、单串口总线、50Hz 控制环路。环路通过一次总线事务读取总线上全部16个设备，计算15个关节目标位置，再写回设备。其余所有模块（客户端、健康状态、遥测）均挂载在该环路之上，不得阻塞环路执行。

1.1 总线与端口所有权

15个舵机与 imu_to_dxl 板卡共用一路UART，不存在第二条总线或第二个端口：

                     robotd — 控制线程
                              │
                              │  duck_control::bus::DynamixelIo
                              │  serialport · TIOCEXCL
                              ▼
         /dev/ttyS2 · 1 Mbps · Dynamixel v2协议
                              │
    ┌────────────┬────────────┴───────┬──────────────────┐
    │            │                    │                  │
  id 200       20–24                30–34             10–14
 imu_to_dxl   左腿        颈部·头部·嘴部     右腿
  v2板卡      5个舵机             5个舵机           5个舵机

IMU 设备ID为200，与舵机在同一次同步读指令中读取。硬件设计如此：v2板卡挂载在 Dynamixel 总线，在舵机共用的寄存器块输出片上SFLP四元数。单块板卡、单代码路径，不做独立IMU抽象。ID列表中将它放在首位，保证在舵机批量通信前完成应答。

同一时刻只允许一个持有者；仅依靠tty独占标志无法实现该约束。serialport 设置 TIOCEXCL，普通用户再次打开端口会返回 EBUSY 忙错误；但 robotd 守护进程以root运行（电机控制需要字符设备），root不受该标志限制。因此守护进程与独立初始化程序使用建议性文件锁，单独防止其他程序抢占端口：

  • 守护进程运行期间，控制环路持有端口所有权。
  • robotd init 会直接打开端口，但必须先获取守护进程的端点锁。在整个斜坡运动期间持续持有锁：正在运行的守护进程会拒绝init；正在执行运动的init也会阻止守护进程启动或另一个init。
  • 守护进程运行时，robot.init 和 robot.relax 为IPC调用（§3.3）；独立init是守护进程未启动时的应急方案。
  • serial-getty@ttyS2：Armbian 默认在UART2启用登录控制台，agetty占用端口会导致所有舵机无法被访问。scripts/setup-board.sh 屏蔽该服务；fuser -v /dev/ttyS2 可查看占用端口的进程，该命令仍用于查询总线占用方。
  • runtime 层面：它复用同一条总线，所以主板只能运行 runtime 或 robotd 其中一个，systemd单元通过 Conflicts= 声明互斥（§5.2）。

Socket所有权 两个入口在创建 /run/robotd/identity.json 或打开总线前，均会获取 <socket>.lock（默认 /run/robotd.sock.lock）。守护进程在启动控制线程前绑定监听套接字，在控制线程退出、套接字清理全程持有锁。重复启动的实例不能覆盖原有进程PID与构建版本：robotctl health 和更新器启动校验会读取该身份信息。旧守护进程遗留的无锁监听套接字，仅在连接探测失败时才会被清理；正在工作的监听端点与模糊路径保留不动。独立init仅加锁，不会绑定或清理套接字。

永远不要删除锁文件，即使是关闭时。内核会在文件关闭或进程退出（包括SIGKILL）时释放建议锁，文件本身保留。删除重建锁文件会导致多个竞争者对同名但不同inode的文件加锁，引发冲突。锁文件存在≠锁被持有。锁以--socket参数为单位；使用同一物理总线的调用方必须使用相同socket配置。独立端点可用于独立的虚拟守护进程。旧二进制与其他工具不参与该锁机制，在独立init接管总线前必须手动停止。

1.3 crate 模块边界

duck-ipc-proto/  有线通信协议：仅serde序列化；无tokio、http、加密
duck-control/    机器人模型、总线、IMU、RobotIo、观测、策略、安全层
                 包含从总线读取到写回之间全部逻辑
                 不依赖tokio、socket、systemd
robotd/          主进程：socket、JSON-RPC、systemd、健康上报
robotd-params/   启动参数：模式、默认值、校验（§4.2）
kinematics/      MJCF模型、正运动学、头部与肢体链
odometry/        机器人位姿估计，基于足底接触与IMU
sounds/          语音：合成、单机器人个性、合唱乐谱
pet-detect/      摄像头侧检测器，由robotd轮询，不在控制环路内
robotctl/        命令行工具
padd/            游戏手柄 → 意图转换
updater/         更新引擎 + updaterd

robotd/ 以下所有模块都是被调用的库，而非独立服务：没有独立tokio运行时、不监听socket、不由systemd启动。拆分为独立crate的原因和duck-control一致：借助编译器隔离守护进程相关逻辑；运动学模块有两个使用者（里程计、robotd头部正解），拆分避免重复复制模型。

duck-control 承载总线读写之间所有逻辑；robotd是包裹它的主进程。编译器强制维护该边界，防止守护进程逻辑污染控制代码。后续迁移时，如果runtime需要复用该模块，可直接拆成独立代码仓库，无需大规模重写。

安全层持有唯一的 RobotIo 写句柄：策略、控制器、所有客户端都只能生成目标值，无法直接下发电机指令。由Rust借用检查器保证，不是单纯代码约定（§2.4）。

1.4 控制节拍（tick）

50Hz，独立tokio任务使用专属运行时，保证IPC任务不会抢占控制环路。每个节拍2次总线事务，每秒额外执行一次慢速传感器读取：

read()          一次快速同步读 · IMU板卡 + 15舵机 · 寄存器124–136   (§2.1)
decide          观测值 → 策略推理 → 目标关节 → 限幅                 (§2.2–§2.4)
write()         一次同步写 · 目标位置
publish         原子变量永久更新；状态帧仅在有订阅者时发送            (§4.1)

每1秒       slow_sensors()     · 寄存器144–146 · 电压 + 温度 (§2.1)

数据流图之外的决策逻辑：

启动流程
    ├─ 打开总线（持续等待）       板卡断电通过开关恢复，不直接放弃环路
    ├─ Safety::new(io)            安全层获取RobotIo；其他模块无法写电机
    ├─ read() → hold = 当前姿态    启动时不主动运动
    └─ 策略
         禁用 ─────────────► controller = None                    状态健康
         加载成功 ─────────► controller = Some
         加载失败 ─────────► controller = None + policy_error   状态不健康

每个节拍
    读取 ─┬─ 成功  ─► 清空连续错误计数
          └─ 失败 ─► 计数+1，传感器数据置空（节拍继续运行）

    观测 → 是否摔倒?     对外发布；不阻断任何控制

    driving = 启用 ∧ 策略加载成功 ∧ 本节拍传感器有效 ∧ 非跌倒缓降状态

    状态跳变 ─┬─ 开始驱动 ──► controller.reset()
           │                      防止陈旧动作、滤波器基于旧姿态导致机器人突然晃动
           └─ 停止驱动 ──► hold = 捕获当前姿态
                                  每节拍重复读取会因重力导致姿态下垂

    driving ─┬─ 跌倒缓降 ─► 使用缓降序列的目标与增益    (§2.4.1)
             ├─ 正常驱动 ─► step() → 目标、增益、当前网络名称
             └─ 停止驱动 ─► 目标=保持姿态，默认增益，标记"held"

    safety.apply(targets, hold, gain)

    发布 ─┬─ 原子变量            永久更新      → robot.health, safeToRestart
             └─ 状态帧        仅订阅者接收   → robot.state

驱动生效的4个条件缺一不可。本节拍传感器有效是容易忽略的约束：读取失败就没有观测数据，不能凭空编造观测输入给策略模型。非跌倒缓降不是拒绝条件：当跌倒缓降序列接管机器人（§2.4.1），策略主动停止驱动，目标由缓降序列生成。

环路使用tokio interval任务，不采用硬实时（§5.4）。相比runtime的重要改动：MissedTickBehavior::Skip。

  • Burst：积压的tick一次性连续执行，电机指令堆叠。
  • Delay：每次完成后按now+周期调度下一次，唤醒延迟不断累积，环路变慢。
  • Skip：维持原始调度，丢弃错过的节拍，正是控制环路需要的行为。 感知模块迁移到mediad，消除了大部分与环路抢占CPU的负载。

1.5 不变量（核心约束）

所有设计围绕下面5条属性，每条都有强制校验，不是单纯设想：

  1. 安全层之上任何模块不能直接写电机。安全层持有唯一RobotIo，Rust借用检查器强制保证（§2.4）。
  2. robotd不会因为进程启动而自动移动机器人；更新重启时，站立机器人保持原有姿态（§3.3）。
  3. 控制环路永远不会阻塞等待客户端。意图采用原子加载；遥测数据滞后丢弃（§4.1）。
  4. 健康状态是主动发布，而非被动查询。环路卡死时会上报不健康，而不是阻塞调用方（§3.4）。
  5. 只有版本发布本身导致的故障才计入健康判定。电池电压、温度仅作为描述信息，不作为自动回滚的触发条件（§3.4）。

2. 控制链路

2.1 总线层与RobotIo

基于rustypot的轻量封装：打开端口、快速同步读、同步写目标位置、扭矩开关、增益设置、慢速传感器读取、启动寄存器校验。代码重新编写，但参数取自runtime，附带注释标注来源。

RAD_PER_SEC_PER_COUNT = 0.229 × 2π/60，用于位置计数值 ↔ 弧度换算。

check_and_fix_config 启动时校验并修复EEPROM寄存器：return_delay_time=0、baud_rate=3、pwm_slope=255、shutdown=52。 return_delay_time=0至关重要：XL330默认值250会带来每个设备500µs应答延迟，16个设备单周期约8ms，占用40%时间预算。舵机恢复出厂或更换后会回到默认250，该校验解决一类“机器人运行缓慢”问题。shutdown=52为错误掩码，捕获过载、过热、输入欠压故障。

舵机自动适配：替换新舵机无需手动配置。全新XL330默认ID=1，波特率57600，本总线不使用该参数。打开总线时先ping15个预期ID；恰好一个设备无响应时，寻找ID1：先1Mbps，再切57600波特，写入目标ID与总线波特率，切回1Mbps，执行寄存器校验，重启舵机。重启清除flash残留硬件告警，否则舵机会持续关闭扭矩直到断电。完整总线只会执行15次ping；只有舵机缺失才触发57600探测。两个及以上舵机缺失则不处理，日志记录，无法判断新舵机对应哪个位置。

位置P增益写入时I、D置0，沿用runtime --ki/--kd 默认值。这是RAM寄存器，上电复位恢复出厂值；出厂D不为零，保留会抑制舵机内置PID，同等kP下机器人明显变软。该参数固定，不对外暴露。

每节拍2次总线事务，每秒额外一次慢速读取。节拍读取连续寄存器124–136（PWM、电流、速度、位置）。电压、温度位于144–146，与前面间隔12字节轨迹寄存器。因此每秒单独一次事务读取电压温度（约1ms），而不是50Hz下把每个舵机读取长度扩大到22字节。采样窗口和实际环路频率测量共用同一时钟源。

电压取舵机均值：15个舵机共用一块电池；返回0的设备过滤，不参与平均，避免误判电池半电。温度不做平均：上报每个关节温度并输出最高温关节名称。膝盖深蹲时温度远高于嘴部，平均值会掩盖接近过热停机的关节。

舵机无应答会导致整个同步读事务失败：rustypot同步读等待全部ID，任一设备无应答则本次事务失败。两次读取均为全有或全无；读取失败时保留上一次采样值，不把单次丢失当作有效事件。

所有同步读使用快速同步读（协议2.0指令0x8A），控制器全局开启。指令包格式和普通同步读一致，应答方式不同：不再返回16条独立状态包（各带10字节协议头+设备应答延迟），所有设备把数据块追加到广播ID的单条应答包。总线每周期只一次应答翻转，以此配合return_delay_time=0降低开销。其余普通总线事务仍会按设备产生延迟，寄存器校验依然必要。

快速同步读同样全有或全无：设备固件不支持0x8A指令则完全不响应，读取超时，不会返回部分数据。XL330固件必须≥v46；ID200的imu_to_dxl板卡也必须实现该指令。

这是固件层面约束，软件无法绕过。所以bus.fast_sync_read默认开启，作为可配置项而非硬编码常量。关闭后所有同步读退化为普通模式，行为和未启用该指令时完全一致；open_bus会在日志打印该状态，否则慢速模式和性能差的机器人无法区分。

默认开启是激进方案，但故障现象明确：不支持0x8A的设备完全不响应，所有读取超时，不会返回似是而非的数值。环路第一拍就上报总线丢失，min_achieved_hz判定不健康；启用该功能但固件不支持的版本会自动回滚。旧固件机器人需要手动设置一次参数；启动阶段不做版本协商和探测，因为无应答设备和断电设备现象一致，探测无法区分。

板卡温度是第三路传感器，不在电机总线。读取SoC所有热区的最高温度，来自sysfs，每秒采样（robotd/src/soc.rs）。放在robotd而非duck-control：属于Linux主板属性，不是机器人本体。电机总线失效时仍然可读，用来区分“通风口堵导致主板过热”和“舵机损坏”。取所有热区最大值，避免传感器布线差异导致漏报高温通道。

同时读取热损耗信息（温度无法直接体现）：同一采样读取时钟上限（scaling_max_freq / cpuinfo_max_freq）与cpufreq冷却状态。Radxa Zero3在95℃时热管理会把主频锁在408MHz（最大1800MHz），不足原调参CPU的1/4，高温下机器人步态变差就是CPU降频导致。仅温度只能提示“需要关注”；温度+频率限制才能判定机器人性能受损。

两项读数缺一不可：冷却状态标识热为根源，但只是频率表索引，“6/6”看不出损失多少；主频上限反映损失，但也可能是用户态策略。取最差热区和最深cpufreq冷却状态，和最高温逻辑一致：大小核主板优先降大核，只看policy0会误判，控制环路所在核心已经降频却显示主板空闲。

永久跟踪IMU数据陈旧问题：读取成功但返回重复采样值，会给策略送入错误姿态，该问题不易察觉。总线层保存上一帧数据，统计连续重复样本，持续足够时间（0.5s，和SFLP解码器判定有效测量的等待时间一致）才写入日志。首次重复不告警（避免日志刷屏）；超过阈值后限流输出，防止50Hz重复告警填满日志。

抽象接口：

#![allow(unused)]
fn main() {
trait RobotIo {
    fn read(&mut self) -> Result<Sensors>;                 // 关节+IMU，单次事务
    fn write(&mut self, targets: &JointTargets) -> Result<()>;
    fn set_gain(&mut self, kp: u16) -> Result<()>;         // 每个关节单独写，非每节拍调用
    fn set_torque(&mut self, on: bool) -> Result<()>;      // 同上
    fn slow_sensors(&mut self) -> Result<SlowSensors>;     // 电压+每个关节温度
    fn imu_stale(&self) -> ImuStale;                       // 默认实现
    fn imu_ready(&self) -> bool;                           // 默认实现
}
}

set_gain、set_torque每个关节一次总线事务，不在每节拍调用。上电使能采用状态机，而不是循环持续设置标志（§3.3）。两个不属于trait的辅助方法仅init使用：present_positions（轻量读，启动一次性读取当前姿态）、interpolate_to（阻塞线性斜坡；刻意阻塞，运动期间不允许其他总线访问）。

两个实现：DynamixelIo（真实硬件）、FakeIo（脚本化模拟采样，可冻结/模拟故障）。FakeIo用于单元测试，cargo test无需硬件、网络、Docker。

macOS不使用条件编译关闭该模块。原本想把serialport排除在macOS依赖树，但rustypot与serialport均可编译，该条件编译没有收益，反而失去无硬件板卡时的类型检查。仅打开真实端口的入口做条件编译。Mac编译后不会模拟机器人；robotd --fake是mac上的测试方式，必须手动指定，不会自动降级。

2.2 观测向量生成器

所有alpha策略统一：obs[1,61] → actions[1,14]；已在行走、站立、地面拾取、踢球、坐姿场景验证。固定布局：

[ gyro(3) | projected_gravity(3) | joint_pos(14) | joint_vel(14) | last_action(14) | command(13) ]
                                                                    command = vel(3) + head(4) + body(6)

嘴部关节不纳入观测；动作输出映射回15路电机，索引9置0。旧的51/54D、49D轮式、85D追踪观测布局随硬件变体废弃。

指令向量（command）是唯一曾经存在争议的部分，直接取自原型control_step，不猜测定义：

  • 48..51：vx, vy, vyaw
  • 51..55：neck_pitch, head_pitch, head_yaw, head_roll
  • 55..57：body x, y — 硬编码0，训练时不绑定
  • 57..60：body z, roll, pitch
  • 60：body yaw — 硬编码0，训练时不绑定

三个容易踩坑点：

  1. body全零是标准编码，不是占位符：x,y,yaw固定为0代表“未绑定”；z/roll/pitch仅在身体姿态模式启用时非零。
  2. 头部目标在command内，不是叠加在策略输出之上。原型在不同模式两种方式切换，通过!new_cmd_obs控制叠加，注释：head_offsets作为command送入观测向量，不要二次叠加。两者同时启用会导致头部偏转两次。
  3. body段顺序是 z, roll, pitch，不是z,pitch,roll；顺序颠倒会导致前倾指令时机器人侧向倾斜。

2.3 策略模块

刻意沿用runtime结构。robotd/src/control.rs保存优先级链和全部取自control_step的数值默认参数，替换原有逻辑。

技能窗口 ← 更新/过期（特技窗口、踢球计时器、拾取阶段、坐起/站起过渡）
指令     ← 客户端平滑指令，编码适配当前激活技能
网络     ← 特技 > 踢球 > 地面拾取 > 坐起/站起 > 按幅值站立(或强制站立) > 行走
动作     ← ONNX推理
目标姿态 ← 零位姿态 + action_scale × 动作输出
滤波     ← 头部、腿部一阶低通滤波

原型两个细节需要保留，容易被误改：

  • 踢球窗口使用站立调参：踢球观测向量command全零，触发站立过渡，因此踢球使用standing_action_scale与站立柔化增益。保留该逻辑，因为踢球参数基于该设定调优。
  • 坐起→站立上升阶段同样使用站立增益（command全零），坐姿不使用（姿态标志把扭转幅值置1）。同一机制，理由相同。

一处刻意改动：原型在状态切换时保存恢复action_scale，坐→站切换后可能残留旧值，直到下一次行走。本实现每节拍基于当前状态重新计算scale与增益。

策略文件路径在参数文件配置，默认指向发布目录。正常更新会携带配套训练策略；开发者可自定义onnx路径迭代，无需打包新版本。

策略文件选择（正式版本、Hub组件、开发者上传文件）由 policy-channel-design.md 定义，包含切换命令与加载失败处理。本节只定义策略本身、校验、运行逻辑。

校验在加载阶段，而非推理阶段：观测向量长度、动作输出维度、ONNX Runtime是否存在。所有网络必须61输入14输出，加载阶段校验，不能运行中途发现错误。runtime旧51维观测模型仅在--new-cmd-obs=false加载，robotd拒绝这类模型，报错观测宽度51，预期61。环路启动前执行预热推理，消除首推理耗时（避免被误判为丢deadline），同时验证动态库加载成功。

缺少ONNX Runtime时ort会panic。它在setup_api内部懒加载，任意API调用都可能触发，无法捕获为普通错误；一旦panic会杀死控制线程，环路永远无法完成节拍，上报“环路未完成周期”，表现为卡死，比本设计要规避的崩溃重启更差。policy::ensure_runtime使用和ort相同的加载器与搜索路径，提前探测动态库，缺失时转为普通错误。

policy.enabled区分两种状态：不启用策略（健康，用于更新器测试）和策略损坏（不健康，触发版本回滚）。合并两个状态会导致测试机器人误报故障，或损坏版本通过校验。robotd --no-policy开启该模式，CI与笔记本无ONNX Runtime，测试使用该参数。

ONNX Runtime为板卡前置依赖，由scripts/install.sh安装，不打包进发布包。它更新频率远低于守护进程，每个版本包附带20MB会无谓增大更新包。代价：缺少该库的板卡安装启动正常，但无法行走；健康状态会输出库搜索路径。

暂未实现：预绑定ONNX输入输出张量。当前每次推理分配61个float向量，50Hz下约244字节。需要在板卡实测后再优化。

从runtime继承经过验证的逻辑：头腿低通滤波、动作缩放、电压自适应缩放、站立过渡增益切换。属于可调参数（§4.2），不重新设计。低通alpha值必须和alpha策略训练所用完全一致，否则迁移效果下降。原则：不破坏已经能正常运行的功能。

2.4 安全层

安全层持有唯一RobotIo写句柄。策略、客户端都没有写句柄，安全约束是结构上不可突破，不是靠人为遵守约定。和更新器的故障恢复逻辑理念一致：仅在异常时才执行的代码最容易静默失效；直接让非法状态无法编译表达。

两条无条件规则：

  1. 拒绝非有限浮点数：NaN目标不会限幅，直接拒绝。
  2. 执行执行器范围限幅：每节拍把目标限制在舵机物理行程。这是舵机硬件范围，不是关节解剖限位；捕获NaN、不合理动作缩放、异常张量；不能阻止关节进入机械危险位置（§9.3）。

外加指令看门狗：意图停止接收，速度置零。停止不等于缓降，区分很重要：通信丢失，双足机器人保持站立（安全状态）；失衡是另一类事件，不由该层处理。

摔倒判定仅为上报，不阻断控制。每节拍计算躯干坐标系下的投影重力，0.2s防抖，避免足落地误判摔倒；判定结果对外发布，但不阻断任何逻辑。摔倒的机器人依然可以启用、初始化、执行运动、调用技能。设计意图：倒地时恰恰需要这些接口可用；如果重力误判倾斜就自动停止，机器人会反复坐下。摔倒后的恢复逻辑放在上层，无需特殊豁免。早期版本曾有fall_limp阻断和自动站起，已移除：恢复逻辑需要绕过的安全规则，就不是有效的安全规则。

2.4.1 摔倒属于独立事件

前面的摔倒判定回答“机器人是否已经倒地”，适合上报侧翻；但不适合做落地缓冲：重力持续200ms低于fall_gravity_z时机器人已经倒地，缓冲窗口期已经过去。

因此limp_fall（默认关闭：默认velstand步态不加载站立网络）独立检测器duck_control::fall，基于角速度而非位置。躯干坐标系下投影重力随躯干旋转，$\dot{g}=-\omega\times g$，直接取自IMU12字节数据；外推0.3s预测重力走向。当机器人倾斜约26°、持续倾倒无法恢复、预测超过摔倒阈值，防抖3个节拍触发。直接对SFLP四元数求导会叠加滤波器延迟，而该信号需要提前预测。

该机制目标不是缓冲落地，而是摔倒之后的站起。站立策略在姿态稳定时可以干净站起；如果机器人倒地挣扎，多次尝试行走增益会带来巨大电机负载。因此该序列接管控制：以gain_limp跟随关节缓慢下放，等待陀螺仪稳定，约1s斜坡回到站立姿态，交还控制权。交还时扭转指令保持为0，指令幅值选择站立网络，完成站起。

实现上脱离策略主路径：整个缓降阶段driving=false（§1.4），目标由缓降序列生成，通过apply和其他目标一样下发电机；没有特殊豁免、后门。安全层无需额外配置，因为摔倒判定不阻断控制；斜坡运动对倒地机器人和正常机器人处理逻辑完全相同。

调参是非对称设计：假阳性触发缓降会主动制造摔倒，比硬着陆更糟，因此默认参数偏向晚触发。

电池耗尽是另一种非指令运动：开启safety.battery_empty_shutdown（默认启用），平滑电压达到低压阈值时机器人下蹲，板卡断电。EMA滤波窗口约10s，负载压降不会误触发；电压降到6.6V代表电池真正耗尽。

2.5 机器人模型

仅alpha版本的Rust常量：15个关节，Dynamixel ID 20–24 / 30–34 /10–14，关节名称、默认零位、执行器行程。沿用runtime motor.rs的表，移除废弃变体。仅定义单机器人；硬件改版新增第二套表。

两个表跨crate强依赖：JOINT_NAMES在duck-ipc-proto，因为有线协议按索引映射关节与目标，顺序不能错位，由const断言强制保证。DEFAULT_POSITION必须和训练环境HOME_FRAME一致：策略观测关节位置是相对零位，不一致会导致14个观测通道出现恒定偏移。

3. API接口

3.1 意图输入

两类语义：输入意图、输出状态。JSON-RPC两类消息刚好对应：

// 连续通知：无id，无应答，后写覆盖前写
{"jsonrpc":"2.0","method":"robot.move","params":{"vx":0.2,"vy":0.0,"vyaw":0.4}}
{"jsonrpc":"2.0","method":"robot.head","params":{"neck_pitch":0.35,"head_pitch":0.35,"head_yaw":0.0,"head_roll":0.0}}

// 离散请求：带id，有应答
{"jsonrpc":"2.0","id":7,"method":"robot.stop"}
{"jsonrpc":"2.0","id":8,"method":"robot.enable","params":{"on":true}}

单位全部为弧度，躯干坐标系，右手定则，符号在协议固定。runtime存在一堆符号修正参数--laser-track-yaw-sign等，是因为之前没有书面约定，各客户端自行试错。写入协议规范消除这类问题。

50Hz连续意图采用通知模式，无应答流量。后续走WebRTC时，通知走不可靠遥测通道，请求走可靠控制通道，符合architecture.md §5.2，由消息类型自然区分，无需额外规则记忆。

躯干运动与头部指令分为独立槽位。合并槽位更新一个字段就需要读改写；手柄控制身体、另一模块控制头部会静默覆盖对方指令。独立槽位在实践上单写入者，后写覆盖逻辑符合预期。每个槽带时间戳：环路关心的不是数值，而是数据新旧，看门狗基于时间戳判断。

look（视线方向）暂未实现；两种视线接口后续开放，仲裁策略为后写覆盖，不做混合插值。

3.2 状态输出

可订阅的单一流，支持按订阅者单独降采样。必须上报被限幅的内容，不只是最终执行结果。遥操UI如果显示摇杆前进，但机器人不动且无说明，将无法使用；安全层会持续限幅。

{"method":"robot.state","params":{
  "t":1234.567,
  "move":{"requested":[0.4,0,0],"applied":[0.15,0,0],"limited_by":["max_velocity"]},
  "policy":"walk", "safety":{"fallen":false,"limp":false},
  "loop":{"hz":49.8,"missed":0},
  "battery":{"volts":7.62,"percent":64}
}}

电池同时输出电压与百分比。映射规则：负载状态6.6V空，8.2V满，NP-F550电池，实现在duck_control::model::battery_percent，随数据下发。原型只下发电压，APP本地计算百分比，同一电池两端显示不一致。客户端绘制电池图标不需要知道电池型号。无独立电量计，直接读取舵机供电电压，负载下电压跌落，静置恢复。

robotctl monitor和后续APP共用同一载荷。替代旧runtime的9870端口180字节帧、9871JPEG流、9872 UDP指令、9874/9875地图定位端口、web hub /state.json。新增字段只需要修改单个结构体，旧客户端自动忽略未知字段，不会多处静默不一致。

robot.subscribe将连接转为状态流；环路写入有界广播通道，不会阻塞等待订阅者，慢订阅者丢失片段，和更新器进度上报规则一致。降采样在服务端按订阅者独立配置，10Hz仪表盘相比50Hz数字孪生，对机器人负载更小。

订阅应答返回策略信息SubscribeResult：进程加载的网络文件名，以及无驱动时的说明（参数禁用/加载失败）。握手阶段返回，进程生命周期内不变；state帧内的policy字段回答另一问题：当前节拍由哪个网络驱动。两个版本都叫walk，但开发者对比版本时需要知道网络文件。如果放在state帧，每节拍控制线程分配字符串，而该信息几乎不变。

两个容易踩坑细节：

  1. 无订阅者时不构造状态帧（机器人常态），避免在控制线程无必要分配内存。
  2. 限幅原因直接使用协议字符串，不自动从Rust枚举派生；修改枚举变体不会静默破坏客户端的分支判断。

3.3 上电使能：enable, init, relax

robotd默认不会自动运动。启动读取当前关节位置，作为目标，不打开扭矩。Dynamixel在进程退出时保持最后目标，重启姿态不变，更新过程机器人保持站立。如果启动自动回到零位，每次更新重启会驱动站立机器人，带来摔倒风险，干扰更新器测试。

robot.enable早期只是切换标志；扭矩由独立子命令robotd init打开，需要停止守护进程，无文档，新机器人按下启动无动作：策略运行、环路写位置，但舵机扭矩关闭。因此环路引入上电状态机，robot.enable触发状态推进：

缓降状态 ──enable（策略加载成功+新采样）──▶ 归位（扭矩开启，2s斜坡） ──▶ 就绪 ──▶ 策略驱动

原有不变量保留：进程启动不会自动触发任何动作。更新重启后机器人处于Limp，不开启扭矩，站立机器人保持站立；断言a_restart_asks_for_no_torque校验无写操作，而非写false。改动点：“绝不碰扭矩”这条规则过于宽泛，给每次驱动增加手动步骤。

使能的两个前置条件：

  1. 策略加载成功：enable代表启用策略；如果策略禁用/加载失败就上电，会让机器人在坏版本下站起并保持。
  2. 有效新采样：斜坡从当前关节位置启动；未读取位置直接启动会产生冲击，这正是斜坡要避免的。

机器人倒地不是禁止条件。早期版本倒地时禁止上电，因为当时安全层会在摔倒时保持缓降增益，斜坡站起会失败；摔倒判定不再阻断控制后移除该限制。机器人倒地时调用上电，就是用户想要的站起操作；斜坡正常执行，由站立策略接管。

策略禁用时不会关闭扭矩：机器人保持姿态，即“站立机器人维持站立”。

robot.init与robot.relax是两个独立状态转换指令：“站起”和“松开扭矩”。robot.init曾经是独立打开总线的子命令，relax之前不存在。两者都由robotd处理，不需要停止守护进程；控制环路正在使用总线时，两者不能写总线。init不需要策略：无行走网络也允许站起，CI无ONNX Runtime也能测试上电流程。

指令每节拍读取一次，不是持续标志：set_torque每个关节一次总线事务，持续标志会导致每节拍16次写。后到达请求覆盖未处理的旧请求：20ms内先后发送站起、松开，执行后者。relax清除enable标记，否则下一个节拍检测到驱动请求会再次站起。

两个接口不开放给BLE。手机按键直接释放扭矩会让机器人摔倒；站起会同时驱动全部关节，需要用户目视机器人。

3.4 健康状态，判定边界

方法返回内容
robot.health环路是否按时完成（实际频率+丢节拍计数）；附带描述信息：环路、总线、IMU、电池、舵机、板卡温度、主板时钟上限；健康判定不读取描述字段
robot.safeToRestart策略启用且机器人正在运动时返回false
robot.modelApi常量
robot.remoteSessionActivefalse，mediad维护真实会话状态

健康状态由IPC侧读取环路发布的原子变量（上一次节拍时间戳+计数器）计算，不阻塞查询环路。环路卡死也能上报不健康，而不是挂起调用方。

环路运行在60%目标频率，进程存活、接口可应答，但已经严重故障。控制环路优先实现，再开发行走逻辑，就是为了能区分这种情况（§5.1）。

哪些信息参与健康判定：healthy/degraded是更新系统输入；只有版本发布本身的问题才会触发健康降级。其余信息仅为描述，自动回滚逻辑禁止读取：电池、电机/板卡温度、时钟降频、环路/总线/IMU计数器。 举例：基于电池判定回滚会导致低电量机器人更新失败，反复回滚；高温环境电机温度、主板降频同理，修复热问题的版本会被热保护误判拒绝。

为什么一起返回：用户发现机器人异常，一次查询拿到全部信息；健康判定和原始指标共存，例如不健康：控制环路43.9Hz，missed=0，区分“唤醒延迟”和“负载过高”，两者修复方案不同。robotctl health合并updaterd软件层面信息并打印。

safeToRestart：策略启用且机器人正在运动返回false。行走中途重启电机控制会导致机器人摔倒（updater-design.md §7.2）。

3.5 维护命令独立命名空间

init、紧急扭矩关闭、标定、原始关节写指令不属于意图指令。独立命名空间，转发层可配置传输白名单，禁止远程通道访问。信令控制谁可以连接，但不代表遥操者拥有机械维护权限；update.*指令如果到达DataChannel，远程客户端可触发版本回滚。

4. 环路周边模块

4.1 环路读取快照，永不阻塞

意图和参数由IPC线程写入，环路原子一次性加载快照。没有任何反向背压；遥测通过有界广播，慢订阅者丢失帧，和更新器IPC模式一致。

   IPC任务（tokio多线程）        控制线程（独立运行时，50Hz）
   ═══════════════════════════════        ═══════════════════════════════════

     robot.move  ──► ┌────────────┐
     robot.head  ──► │意图槽位    │ ──原子加载，每节拍一次──► 读取
                     │ twist│head │
                     └────────────┘
                     ArcSwap，带时间戳

     robot.init  ──► ┌────────────┐
     robot.relax ──► │电源请求    │ ──每节拍读取一次──────────► 上电状态机
     skills      ──► │技能标志    │
                     └────────────┘
                     后写覆盖

     robot.health ◄── ┌──────────┐ ◄──────────发布 ─────────── 原子变量
     safeToRestart    │原子变量  │              tick计数、hz、missed、摔倒、运动状态

无反向通道。健康状态主动发布，不按需查询，保证卡死环路可上报。

技能标志使用布尔变量，不是队列：单个20ms节拍内同一按键多次触发无额外意义；两个不同技能请求都需要被捕获，单槽后写覆盖会丢失请求。

4.2 参数配置

TOML文件，启动读取，默认不监听文件变更。文件放在releases/<ver>/之外，更新/回滚保留，路径/etc/robot/robotd.toml，和更新器配置放一起。

两处例外监听，是重启代价过大的妥协，不是全面热加载：

  1. padd每秒stat文件，[pad]和[pad_imu_head_control]修改后重读。手机修改手柄映射，重启padd会断开手柄会话，看门狗会让行走机器人急停。
  2. robotd可按需重读[policy]（mode、enabled除外），robotctl policy add新增技能，无需停下电机控制。

运行中热加载[safety]或[control]是更大承诺，暂不支持。robotctl configure识别不同配置项，非法键会触发测试失败。

文件属于板卡而非版本包：手动修改的策略路径会保留。默认路径指向release目录，普通更新携带配套训练策略；删除覆盖配置就恢复默认。配置文件允许缺失，未配置板卡使用内置默认启动，远程调试比直接崩溃更容易排查。历史教训：注释掉的参数会永久留在该板卡，版本升级不会覆盖，导致一批机器人kP=120，但新版本默认160。

参数约10个，不是142个：控制频率、增益、动作缩放、低通alpha、最大速度、看门狗超时、策略路径、更新门限。runtime大量标记是硬件变体、废弃技能、废弃传感器，现已全部移除。

一个高层开关：policy.mode，walk / roller，选择加载策略与调参默认值，未设置字段按模式填充。切换轮式构型仅改一行+重启。这是预设，不是硬件变体；roller调参来自原型，基于alpha默认参数重构。

4.3 游戏手柄是普通客户端

padd读取gilrs，通过robotd socket发送意图。独立crate，手柄栈不进入robotctl（故障机器人仍需CLI工具可用）。

一次socket转发，微秒级延迟。好处：APP、SDK、远程客户端使用的输入链路，开发者日常同样使用，不会代码长期失活。开发时ssh -L /tmp/robotd.sock:/run/robotd.sock，笔记本手柄控制板卡机器人，无需修改代码。

板卡上为padd.service开机启动，接入任意手柄；无手柄时安全，不发送指令，看门狗保持机器人姿态。进程无特权，这是“手柄作为客户端”的核心约束：仅拥有输入与robot用户组权限。手柄配对属于configd（architecture.md §1），不属于本模块；蓝牙配对需要root+BlueZ，padd不能持有该权限，否则不再能模拟APP使用的API。

4.4 里程计：复用环路已读取的采样

odometry::Odometry::alpha()每节拍基于环路读取的关节位置+IMU四元数更新；估计结果在state流输出odom: { position, yaw }。robotctl monitor在3D视图下绘制轨迹地图。

基于足底接触，移植自原型runtime：单足底作为地面锚点；躯干世界位姿由运动学模型正向求解；另一个足底低于锚点时更新锚点，保证步态不会跳变。航向使用IMU积分偏航角，世界坐标系为机器人开机朝向。无磁力计，不修正漂移，属于相对运动，所有客户端必须按相对位姿处理。

每节拍两次运动学链计算，不增加总线流量，所以和环路同50Hz，而不是原型独立100Hz。之前否决里程计的原因不是计算开销，而是没有模块消费里程计数据；monitor轨迹可视化使用后，该决策被推翻。

第二阶段迭代后新增4个非控制、非安全子系统。共同特点：挂载在tick上，不能阻塞环路；只能通过环路仲裁后的意图访问总线。

5. 设计目标与由来

5.1 目标，不是“写一个更好的robotd”

两个目标，第二个重构了开发顺序：

  1. 快速迭代控制核心。
  2. 真正在硬件上测试更新器。

更新引擎已经完成，但从未在硬件运行。关键路径未验证：on_apply中的systemctl restart没有真实systemd验证；30s健康门限只是猜测；最重要：自动回滚的前提是robot.health含义可靠。早期health只是“环路跑过一次节拍”，之前所有回滚测试都是占位模拟。

所以第一阶段目标不是行走，而是在真实板卡提供可信的健康信号（§3.4）。

5.2 robotd替代哪些组件

robotd逐步替代runtime，runtime包含5个独立职责，仅一项交给robotd：

runtime功能迁移目标阶段
控制环路、策略、电机、IMUrobotd完成
游戏手柄意图客户端(padd)完成
摄像头、球/激光/宠物检测、JPEGmediadM5
Web hub、PWA、大脑指令socketmediad / APPM5+
maploc — 建图、MCL、规划未分配—

两者可以并行部署一段时间，但不能同时运行：单串口总线，唯一所有者（§1.1）。systemd单元通过Conflicts=互斥。

远程APP层不在本文设计范围：基于reachy_mini架构，WebRTC媒体 + DataChannel上JSON-RPC2.0，Rust移植，超出本文档范围。对robotd的唯一约束见§3.5。

5.3 两个迭代阶段，“完成”定义

阶段1 — 保持姿态 tick、总线、模型、RobotIo、可信健康。无策略推理，held_pose是启动读取的固定姿态。目标：总线真实负载，环路时序与健康指标真实；故意发布损坏版本不会失控。可反复执行安装/回滚/断电。 验收标准：robotd稳定保持姿态1小时无总线错误；robotctl update apply安装版本，重启，通过健康门限，机器人不运动；不健康版本自动回滚；更新中途断电可通过boot计数器恢复。

阶段2 — 行走与站立 观测、ONNX策略、安全层、意图接口、手柄客户端。 验收标准：通过意图API在板卡行走；robotctl更新重启，门限校验通过；--unhealthy版本自动回滚。

后续新增功能（技能优先级链、上电状态机、roller预设、跌倒缓降）在该基础上扩展，不改变基础架构。

5.4 回归基准作为验收标准

已有基准测试：bench_dynamixel_bus，50Hz与100Hz下输出实际频率、抖动、读取耗时、总线耗时、占用率、错误、IMU新鲜度。记录基准，robotd性能必须匹配。 本项目不做硬实时工程：不使用SCHED_FIFO、不绑定CPU核心、不mlockall。当前环路已经可靠；目标是保持可靠性，简化外围代码。

6. 测试

FakeIo模拟采样，无需硬件：

  • 节拍超时，health置false；
  • 启动读取当前姿态，不会自动运动；
  • 安全层拒绝非有限目标，限幅执行器范围；摔倒事件不会抢占策略或客户端增益；
  • 跌倒预测器仅在摔倒触发，落地冲击、静态倾斜不触发；姿态斜坡最终回到站立姿态；
  • 意图中断，看门狗置零速度；
  • golden观测向量：mjlab导出（输入，预期61维float数组），提交入库。观测索引错误不会明显崩溃，而是机器人步态异常倾倒。依赖microduck_brain导出（§9.2）。

9. 待解决的开放问题

Radxa板载控制频率。50Hz继承自Pi Zero 2W。硬件板卡到位后已可实测：bench_dynamixel_bus工具与控制循环自带的五分钟汇总报告结果一致。

microduck_brain 应当输出基准向量（golden vectors），用于训练环境的回归校验，而不是作为真值来源。该功能不是产品发布的前置依赖。

不存在单关节限位。安全钳位仅限制执行器行程，可捕获NaN、异常动作缩放、无效张量；但无法阻止关节运动到机械结构上不安全的位置。真实限位定义在alpha MJCF文件（31KB），本项目不直接引入该文件。如果限位只是仿真层面的虚拟解剖限位，就意味着机器人没有真实物理保护。

如果后续需要仿真与真机一致性测试，alpha MJCF存放位置：31KB XML文件 + 19MB网格模型，当前位于运行时脚本目录 scripts/alpha_assets/。

C语言依赖带来的持续开销。Linux下gilrs会无条件引入libudev-sys，因此CI与板卡交叉编译环境都需要安装该库。后续任何需要部署到板卡的C依赖都会带来同样成本，因此这条链路优先选用纯Rust crate。macOS未验证：交叉编译需要aarch64系统根目录，Mac无法提供，因此本地执行cargo board --bins会失败；可使用-p updater -p robotd -p robotctl编译发布版本，或者在Linux环境编译。

遥测映射（API v24）

视频远端的映射模块（当前是笔记本，后续改为服务器）需要从机器人获取三项robot.state未包含的数据：与tof帧对齐的共享时钟、除重力投影之外的IMU原始数据、相机与TOF传感器的安装位姿。三项均为新增字段。

robot.state与tof.frame中的t_ns是CLOCK_MONOTONIC单调时钟，单位纳秒（proto::clock）。保留t与at_us：分别是各守护进程自身的运行时长，只接收单路数据流的读取端仍需要从零开始计数的时间戳。mediad媒体视频模块在同一时刻读取mono_ns与real_ns，因此RTP时间戳（RTCP发送报告使用墙上时钟）可以映射到同一时间轴。

imu: {gyro, quat} 是控制循环读取到的ImuData：躯干IMU，50Hz，无上层处理（文档 docs/design/robotd-design.md §IMU）。原型HAT板载头部IMU目前没有模块读取；后续启用时，它会和tof.frame并行推送，不在此字段内。

frames: {camera, tof} 为本周期基于实测头部关节，通过运动学kinematics::head::HeadFk计算得到的躯干坐标系下相机与TOF位姿（和robot.look求解使用同一套前向运动学FK）；静态几何参数（躯干高度、关节顺序、TOF光束方向、头部零点位姿）由robot.model提供。运动学代码放在独立crate，客户端按需查询，不直接复制计算逻辑。

开销：每次发布周期增加3个小型结构体，仅当存在订阅者时才发送；前向运动学计算耗时约50纳秒。
