# 路线图
状态：已重写 · 日期：2026-08-26（初稿2026-08-05） · 负责人：pierre

本文配套 `architecture.md`（项目构建目标）与 `updater-design.md`（发布交付方案）。本文描述**工作次序与排期**，内容会变动；但架构设计文档保持稳定。

## 当前项目状态
- `updater/`：更新引擎、校验、存储、日志、钩子脚本、前置检查、GitHub/HuggingFace/本地多源、IPC服务、systemd单元 —— **已完成**
- `duck-control/`：机器人模型、总线、IMU、RobotIo、观测数据、ONNX策略、安全层。纯库：无tokio、无socket、无systemd
- `duck-ipc-proto/`：全部`*.`命名空间的线上通信协议，API版本v14。仅依赖serde/serde_json/semver；保证恢复环境不会引入更新引擎的依赖树
- `robotd/`：50Hz主循环，经由安全层驱动行走/站立/翻滚；根据截止时间达标情况与策略状态输出意图、健康状态。M3之后新增：运动学、接触里程计、视线逆运动学、语音、ToF特雷门琴、合唱模块，全部挂载在同一时钟节拍下（robotd-design.md §4.4–4.5）
- `padd/`：游戏手柄转为控制意图，作为普通socket客户端；随版本包发布，开机独立运行。配对手柄即为唯一操作步骤
- `robotctl/`：运维命令行工具 — 更新、健康状态、版本、监控、网络、系统、机器人、手柄、配置、鸭鸣、合唱、特雷门琴、命令补全。依赖duck-ipc-proto，不依赖updater，因此可在故障恢复环境运行
- `configd/`：基于NetworkManager管理WiFi、机器人名称、从SoC序列号生成设备身份、配对PIN码、重启、服务状态上报。`--fake-net`参数可在板外模拟整套服务接口
- `btd/`：BLE传输适配器 — 帧封装、路由子集、BlueZ后端、配对代理。硬件可运行，默认不加密（app-path-design.md §5.5）
- `duckctl/`：笔记本远程控制机器人。当前使用BLE；命名面向机器人本身，而非通信链路
- `mediad/`：摄像头、麦克风、编码、WebRTC网关，附带内置控制台。Radxa Zero 3W局域网内推流至浏览器；硬件H.264编码（mpph264enc），附带控制数据通道
- `tof/`：tofd：头部8×8 ToF矩阵，独立socket，15Hz。无传感器的板子也会启动该服务并上报缺失状态
- `xtask/`：打包、签名、发布升级 — 验证升级前后字节完全一致
- `.github/`：CI、发布、推广、开发流水线；四条流水线全部真实运行。0.2.0之后所有版本均通过这套流程部署到开发板
- bootstrap：updaterd安装 + scripts/install.sh。机器人通过标准更新引擎完成首次部署，不存在单独的bootstrap分支导致代码漂移
- recovery：`robot-boot-check.timer` + robot-rescue + 黄金版本软链接，已打包并默认启用。尚未在实体板上实际触发（boot-recovery-net.md）
- tests：Mac平台942个用例全部通过，Linux上更多；包含健康门限、电池与温度读取、对接真实robotd进程的策略/安全链路，board-test.sh中基于真实socket的configd鉴权测试
- 进行中：maploc (#127)、NPU鸭子检测器、合唱模块选举修复 (#151)；两项仅完成设计PR，尚未编码：手机APP (#107)、IPC监控器 (#52)
- 待实现：手机APP、SDK、策略通道、自主决策大脑、局域网外访问机器人

## 第一版路线图目标已达成
M1～M4是一条连续目标：打造一台可以行走、支持空中升级、且升级过程不会变砖的机器人。目标已实现。0.2.0之后所有版本都基于M1、M2搭建的流水线部署；0.9.x版本的Duck机器人已实现行走、翻滚、视觉、语音、合唱。

后续工作不再是顺序排队。剩余任务为多条独立分支，风险各不相同，互相之间无强制先后顺序。下面的M编号仅为标识，**不代表执行顺序**；工作优先级单独在下文列出。

项目最初判断半对半错：难点是**产品化**而非基础能力，这点判断正确。更新链路、健康校验门限、恢复网络、BLE接口均已落地并稳定。但工作量预估偏差较大。0.5版本之后大部分开发都是能力扩充：运动学、里程计、ToF、视线控制、语音、合唱、摄像头；而最大模块——自主决策大脑，至今尚未开发。

## 里程碑
每个里程碑都有判定“完成”的测试标准，没有验收标准的里程碑容易失控。

### M1 — 闭环控制 · 已完成
更新器拥有真实的校验阻断逻辑；团队确定共享crate边界：robotd核心状态使用原子变量而非互斥锁（即使主循环卡死，机器人仍能上报自身不健康）；拆分出duck-ipc-proto，保证恢复环境不会链接更新引擎的HTTP/压缩/密码库；健康门限基于真实socket探测；robotd socket唯一数据源；所有守护进程异常前输出warn级身份日志；通过标准引擎完成首次安装引导。

验收：`robotd/tests/updater_gate.rs` 通过真实socket对接真实robotd进程，完成更新阻断与提交；`robotd --unhealthy` 会回滚当前版本。

### M2 — 开发版本通道 · 已完成
`sudo robotctl update apply daemon --ref my-branch` 可安装分支构建包；`scripts/dev-push.sh` 通过SSH把笔记本本地构建包刷入设备，无需CI。两条安全约束，独立于工作流强制生效：
1. 开发版不能标记为latest（版本为semver预发布版本，version_under不会将开发标签识别为正式发布版）
2. 不能安装到客户设备（客户机allow_dev_keys关闭；仅文件名以`.dev.pub`结尾的可信密钥才视为开发密钥）

验收：在真实仓库验证；dev.yml发布，`--ref main`可网络安装；客户机配置拒绝同一开发包。

遗留问题现已决策：私有仓库的发布资产需要token访问，客户设备无token，因此仓库私有状态下量产机器人无法下载版本。**决定将仓库公开**，解决该问题，无需修改代码；更新引擎使用的API路径同样兼容公开仓库（updater-design.md §6.1）。

### M3 — 正式robotd · 已完成，分两阶段
robotd不再使用microduck_runtime，而是提取其控制核心至duck-control，而非重新实现；功能对齐来自代码提取，而非追赶持续变动的目标。
阶段1：真实50Hz Dynamixel伺服循环维持姿态，`robot.health`指标代表主循环按时执行。
阶段2：61维观测值构建器、基础站立策略、意图接口、手柄客户端接入。

安全权限在本阶段落地，而非M6：独占总线写入权限，任何策略/客户端都不能绕过安全层直接控制电机：关节限位、摔倒自动松弛、意图安全死锁。

**硬件优先，仿真在后**。硬件上暴露出单元测试无法捕获的bug：ORT在运行时低于最低要求时直接panic而非返回错误，导致控制线程崩溃，健康模块误报故障。

验收：Radxa Zero 3W硬件全部可用；可通过意图API驱动行走；robotctl执行更新后干净重启，健康校验通过；启动不健康的版本会自动回滚。

### M4 — 硬件整机调试 · 收尾阶段
属于**指标测量里程碑**，不是功能里程碑：把预估参数变成Radxa实体板上实测数值。大部分指标随发布顺带完成：非实时内核稳定维持50.0Hz循环（15022次tick仅3次丢失）；总线与imu_to_dxl板在`/dev/ttyS2`正常响应；各区域温度可读取；on_apply阶段的systemctl restart可正常调用systemd；版本提交与回滚校验生效。

日志留存问题通过方案决策而非实测确定：镜像中`/var/log`为zram内存盘；journald开启Storage=persistent，目录本身位于内存：正常重启日志保留，断电丢失近期日志。这是预期设计：持久化记录放在`/var/lib`下的更新历史，每条记录执行fsync（deploy/README.md）。因此原需求“断电日志不丢失”作废，项目不再追求该特性。

验收标准：硬件可行走；robotctl升级后robotd干净重启，健康校验通过；重启后journalctl --list-boots能列出上一次启动记录。前两项已完成；最后一项仅需在板上执行一条命令，是唯一剩余项。

两个指标暂不测量，无依赖等待：eMMC写入耗时、带载电池性能。归入M7（设备状态诊断里程碑）。

### M5 — mediad、WebRTC、SDK · 进行中
代码已在硬件部署。mediad随版本包发布，独立单元运行。摄像头通过VPU编码在局域网浏览器预览：mpph264enc → webrtcsink，约束基线H.264；控制数据通道复用和其他传输相同的JSON-RPC；控制台由机器人自身提供，直接访问URL无需安装客户端（remote-webrtc.md §0，webrtc-console.md）。需要从源码编译两个GStreamer插件（media-bringup.md）；摄像头已通过rkaiq实现3A自动曝光/对焦/白平衡。

三项待完成内容：
1. **局域网外远程访问**：采用带中转服务+TURN的相同架构，后置开发。remote-access-design.md负责该模块：OAuth设备授权流程接入Hugging Face账号；桥接mini机器人群已在用的Rendezvous Space与机器人内置信令服务器。
账号模块已完成（第一部分）：`robotctl account login`输出验证码，用户在hf.co/oauth/device确认；机器人持有可自动续期的凭证。同一三组接口支持BLE（无WiFi机器人唯一链路）和数据通道。凭证消费逻辑尚未实现：下一步开发桥接模块；Rendezvous Space协议为HTTP，而非局域网客户端使用的WebSocket。
Duck正式发货前需要修复：设备码客户端默认获取该账号全部权限范围，没有scope参数。需要在组织内创建公开OAuth应用，限定scope为openid profile read-repos，配置一个常量。

2. **SDK与轻量Python客户端**。§5.3设计方案：WebSocket+快照，复用JSON-RPC，无媒体栈，get_frame返回JPEG，仅几十行代码；mediad会话层原生支持这套接口（mediad/src/session.rs）。
另一种方案：Python客户端基于WebRTC，单连接同时获取实时视频+控制通道，但需要aiortc、ICE协商与信令交互，代价更高（用户仅下发意图、读取画面时太重）。需要评估：一套客户端同时支持两种模式（WebSocket用于控制/截图；用户请求流时启用WebRTC），还是脚本只使用WebSocket，实时视频留在网页控制台。评估结论决定SDK是几十行的轻量库，还是大型项目。

3. **隐私**，拆成两点。会话授权：视频流启动前需要每会话显式同意，mediad会话层修改，无依赖阻塞。硬件状态指示灯：需要软件可控LED，但当前硬件没有（remote-webrtc.md §11）；属于硬件问题，不应卡在软件里程碑。architecture.md §7结论：现在实现成本低，后期改代价极高，**会话授权不必等待LED硬件**。

验收：局域网外远程可视化可用；服务端脚本几十行代码即可获取图像帧并下发控制意图。

### M6 — 产品发布就绪
面向普通用户的能力。预售已开启，优先级按**交付周期**排序，而非开发难度：代码改动越少的项，供应链/生产准备周期越长。
- 配对PIN码：BLE配对安全依赖单台机器人独立PIN；出厂默认000000，代码仓库公开，开箱配对仅证明物理接触，安全不足。需要工厂流程生成、打印并记录PIN，不是代码补丁。PIN不能从设备身份生成（身份会在广播报文内发布）。
- 标定：设备初始化的另一半。设备身份不再依赖标定：机器人从SoC序列号生成身份，命名为duck-c51b。
- 恢复网络，实体板实测。代码已打包启用，但从未在守护进程启动失败的版本上触发（这是唯一关键故障场景）。最低成本验证：一块板子，刷入一个故意损坏的版本。
- 会话授权（继承M5）
- 清单过期上报（§8.4.2）
- 权限仲裁，已完成，包含#52暴露的边界问题：`Call::is_mutating()`没有覆盖robot.enable，启动行走机器人策略的调用被归类为普通hello消息。
- 手机APP：#107仅完成设计，未编码。阻塞点：手机端原型开发，在真实iPhone和安卓设备完成扫描、连接、握手、鉴权、带`--require-pairing`的system.info。§5.5目前仅在笔记本CoreBluetooth上验证。

已决策移出M6：客户机器人下载源。决定公开本仓库，量产机器人无需token、不需要额外服务器拉取版本。后续需要评估预算，不是阻塞项：匿名GitHub API单IP上限60次/小时；单台Duck远低于限额；同一WiFi下20台设备会触及上限（§6.1）。

验收：非开发人员可以用手机升级机器人；故意刷坏的版本，无需笔记本即可自动恢复。

### M7 — 设备状态诊断
用户拿到的Duck发生故障，当前只能由开发者SSH读取日志定位。方案尚未定型，属于开放性调研课题。

现有能力：`robotctl health`上报总线、IMU、电池、各电机温度、SoC；`robotctl monitor`可视化主循环、手柄流、ToF矩阵、3D机器人模型与功耗；`scripts/pad-stack-report.sh`提供范例，把子系统完整信息打包为可粘贴文本；board-test.sh包含60项检测，但运行在CI的aarch64模拟器而非实体板。

待解决问题：
1. 诊断打包脚本：故障后一条命令导出可发送的诊断包。目前没有工具一次性汇总健康状态、版本、日志、更新历史、服务状态。`robotctl update show`是子系统范例，生成带对应时段日志的持久记录，但只覆盖更新模块。
2. 非开发人员可执行硬件自检：总线扫描、各伺服状态、IMU有效性、ToF/摄像头/NPU/麦克风喇叭检测、电池带载测试。思路接近board-test.sh，面向硬件而非软件版本。
3. 历史记录：偶发故障无法靠快照定位。总线读失败、tick丢失、伺服温度尖峰、电压跌落。M4设计日志断电丢失，因此关键故障记录需要复用更新历史的持久存储，而不是journal日志。
4. 和#52 IPC监控器设计重叠：IPC监控是本问题的软件部分。崩溃日志持久化在`/var/lib`固定大小文件，不在版本目录，升级/回滚不会丢失，正好满足硬件故障报告的持久化需求。两者统一设计，不要两套独立方案。
5. M4遗留两个测量指标归入此处：eMMC写入耗时、电池带载测试。

验收：非开发人员故障后执行一条命令，输出报告，定位故障部件或判定硬件正常。

### M8 — 策略通道：从Hub拉取策略
旧方案：所有策略打包在守护进程镜像内。新步态必须发布完整daemon版本；笔记本训练的策略只能通过CI或者完整daemon侧载部署。
本里程碑目标：microduck_rl（私有训练仓库）训练出的策略，可独立发布、安装、测试、回滚；用户也可以加载别人训练的策略。

设计文档：policy-channel-design.md，确定全部之前悬而未决的规则。简述：策略槽位来源分三类
- 官方：pollen-robotics/*，重置默认目标
- 社区：任意Hub仓库，无签名，会上报状态，但不会自动应用
- 本地：板上本地路径
policy load写入配置项，policy reset清除配置；持久化与回滚复用现有机制；官方策略打包为独立policies组件，而非每个槽位单独包。

引擎大部分已实现：hf_hub源解析校验、组件独立版本链、回滚、版本锁定、启动试跑、已知坏版本记录；on_apply支持reload；xtask sign可对任意制品目录签名。

分三阶段，每一阶段可独立交付：
1. 本地离线链路。`robot.loadPolicy` + 归位姿态重载；robotctl policy list / load / reset。实现“不用修改toml文件测试策略”，不访问Hub，不涉及发布逻辑。API_VERSION 17 → 18。
2. 官方策略脱离daemon镜像。已完成。robotd读取`/opt/robot/policies/current`；scripts/seed-policies.sh从pollen-robotics/microduck-policies下载锁定版本，和setup-board.sh加载ONNX Runtime方式一致。移除policies目录与三组--include列表；更新`[workspace.metadata.policies]`版本号即为步态版本发布。
3. 脱离固定版本锁定。已完成。updaterd增加policy.*接口、robot.reloadPolicies、robotctl policy check / update。训练后的步态不用发布daemon版本即可部署，这是本里程碑核心目标。每个策略包记录来源仓库，避免重复配置。
4. 社区策略库。已完成。`policy load <slot> <org/repo>`从任意Hub仓库拉取策略到`/var/lib/robot/policies/<org>/<name>/<rev>/`；来源标记为community；policy search列出可用策略。已发布仓库自带manifest.json，包含obs_len、action_len、model_api，无法运行的策略下载前直接拒绝；model_api从“仅设计未实现”进入落地规划。

reset统一含义：清除覆盖配置，重新解析策略源。阶段1可正确回滚内置策略；阶段2修改解析源，无需改动reset命令。

真正缺失的部分在两端，中间链路已完成：
- robotd无法按需重载策略。底层能力已有：robot.setMode在归位姿态重建所有ONNX会话，但缺少按槽位触发的接口；加载失败时必须保持原有控制器，不能让机器人失去步态。
- 策略打包发布工具：xtask package --channel接近需求，但会校验crate版本号，策略包没有crate版本；HF仓库目录结构尚未搭建。
- model_api两端仅设计未实现：robot.modelApi可应答，但没有模块读取该参数。
- 训练链路：microduck_rl导出ONNX，但没有自动推送至机器人的流程。阶段1让“训练→测试”从CI流水线改为分钟级本地流程。

验收：microduck_rl训练策略发布到Hub，安装到Duck，测试，robotctl policy reset回滚；全程控制回路不丢失电机控制；其他人可在机器人上检索并加载该策略。

### M9 — 自主决策大脑
最大的待开发模块：运行时autonomous.rs在守护进程中完全不存在，暂无设计文档承接。ideas/autonomous_behavior.md为草稿：基于能量/情绪模型的16状态机、新奇网格探索、ToF避障、惊吓反应、声音交互、玩球、小憩周期、抚摸交互。

现在所有输入源均已就绪，部分新增：环境声音事件、深度帧、躯干障碍物分类点、语音标签、附近Duck稳定ID、共享节拍、RSSI粗略距离、实时合成语音、ToF手部距离。

架构形态比状态机更重要：在场感知、情绪、节拍是大脑的输入，不是独立模式。合唱、特雷门琴过去作为独立模式实现，是因为没有统一大脑承载（合唱模块55KB，位于robotd）。本里程碑目标就是杜绝这种实现模式。**先写设计文档，再写代码**。

验收：Duck单独留在房间，能持续自主行为10分钟以上；合唱是机器人自主决策触发，而非命令启动。

## 工作执行顺序
M编号仅为标识，下面是实际优先级：
1. M8 策略通道。下一个核心功能。不阻塞其他任务，但打通机器人行为迭代闭环：训练 → 发布 → 安装 → 测试 → 回滚。
2. M5 传输方案调研。工作量小，结论决定Python SDK是几十行轻量库还是大型项目。
3. M6 随产品临近，按交付周期推进：客户机器人下载源 → PIN码 → 恢复网络硬件测试。会话授权可以尽早落地。
4. M7 — 调研项，无固定时间表。一旦用户设备出现无法定位故障，优先级拉高；最优方案是和#52 IPC监控一起设计，而不是后置。
5. M9 自主大脑 — 有意延后开发。剩余工作量最大，开发过程范围容易膨胀。

## 影响整体架构的决策
- 签名密钥保管：daemon相关已完成。3个加密发布密钥 + 未加密开发密钥存放`~/.duck-keys`；仅release-1录入secrets。CI在release环境签名，隔离密钥，但不做强制准入（无评审人、分支保护）。在无量产设备阶段主动接受该方案；后续只需修改配置即可启用严格校验。详见ci-setup.md。M8策略发布引入第三类密钥，该议题会重新讨论。
- 安全权限（§6）：M3落地完成。
- 设备初始化：身份模块完成；标定、PIN未完成；PIN属于工厂流程，不是代码（M6）。
- 隐私：会话授权在M5，无阻塞；指示灯是硬件问题，单独评估。
- 客户机器人下载源，2026-08-26决议：公开仓库，机器人直接拉取版本。§6.1保留其他备选方案与理由，作为仓库再次私有化时的降级预案。
- 策略是否脱离daemon镜像：倾向于可以，尚未最终敲定。策略外置，缺失模型上报为降级（degraded）而非不健康，允许更新提交；初始化脚本预装基础策略。M8会评估该方案不稳定时的备选方案。
- 精选模型库还是开放社区库：开放社区，属于信任策略，不是底层技术问题（M8）。
