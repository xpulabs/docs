# 无人访问时的头部传感器
对于所有搭载头部模块的Duck机器人，`tofd`进程会从开机到关机持续驱动激光测距并读取IMU数据，无论是否有进程订阅这两路数据流。项目最初的设想是**按需启动设备，用完即停**，但经过逐步骤实测后方案大幅简化：深度流本身几乎不消耗资源；真正占用CPU的传感器完全没有消费方，并且其循环内部不存在值得优化的逻辑。因此激光与测距单元保持原有逻辑不变，而为头部IMU增加开关，**默认关闭**。

本文承接`idle-cpu.md`文档的工作：该文档将`tofd`的I²C轮询频率从约100次/秒降至45次/秒，但并未解释为何需要持续轮询。

## 实测资源开销
测试平台：olducky（Radxa Zero 3，RK3566），板卡空闲，无任何订阅连接：
```bash
$ ps -L -o tid,comm,pcpu -p "$(pidof tofd)"
    TID COMMAND         %CPU
  12209 tofd             0.0
  12212 tof-sensor       0.5
  12213 head-imu         4.5
```
百分比为单核占比。`tofd`总CPU占用约5%，折算到整个SoC为1.25%；其中**头部IMU占9成，深度传感器仅占1成**。负责socket通信的运行时，在没有业务需要处理时几乎无开销。

这个CPU占用拆分就是本文核心结论，由此引出两点推论。

IMU的CPU开销主要来自**单次采样的两次读取**，不是唤醒开销，也不是姿态融合开销。在停止`tofd`的前提下，在该开发板上运行crate内`bench_imu`基准测试：以100Hz频率，每种模式连续运行10秒：
```
仅休眠（0次读取）    CPU 0.69%
仅滤波（0次读取）    CPU 1.00%
update（2次读取）    CPU 3.35%
update_all（2次读取）CPU 3.86%
三次读取（3次读取）  CPU 4.20%
```
每秒100次任务唤醒带来0.69%开销；Madgwick姿态融合增加0.31%；剩下约2.4~2.9%来自两次I²C通信。陀螺仪与加速度计采样需要从两个地址读取共12字节数据，完整采样**最少必须两次I²C事务**——这也是该循环内部没有优化空间的根本原因。

基于该数据做决策，有两点需要注意：
`update`与`update_all`执行的逻辑完全一致（一个函数内部调用另一个），但测试结果相差0.51个百分点，说明噪声底大约0.5个百分点，大概率来自A55内核的CPU调频。
早期另一组同三模式测试，当时`tofd`仍占用I²C总线，三组结果被压缩至4.44/4.46/4.53，看起来第三次读取几乎不耗资源。
但两种测试的趋势不变：**读取操作是主要开销，噪声底很小；第三次读取带来0.3~0.9%的CPU开销**。

**当前没有任何模块订阅头部IMU**。在本代码树中，`head_imu.stream`没有消费方：
`btd`不转发该数据流（btd/src/route.rs:412）；更新器降级IPC拒绝该订阅（updater/src/ipc.rs:819）；没有守护进程订阅。
该传感器原本是为建图功能新增，但建图模块尚未落地。也就是说，这个守护进程里最大的持续资源开销，来自一个无人使用的传感器采样。

> 需要明确区分：行走策略所用IMU是**另一颗芯片、另一路总线**，位于Dynamixel总线上的imu_to_dxl v2板卡，和15个舵机一同在50Hz同步读取（duck-control/src/bus.rs、duck-control/src/model.rs:76）。本文的改动完全不影响它，不会造成行走策略缺失IMU采样。

## 最终决策
`[head_imu] enabled`，**默认关闭**。IMU循环内部没有值得优化的点，因此采用开关方案：一条没有任何订阅者的数据流，不该从开机起就占用单核约4%算力。
配置项写在`robotd.toml`中，`mediad`已经读取同文件的`[media]`段。`robotctl configure`可以修改该配置并提示重启`tofd`；
`tofd --imu`可以单次会话读取芯片，**不修改配置文件**；当头部IMU开关关闭时，订阅方收到的报错会明确指向该配置项，而不是像传感器未安装那样直接静默。等到建图模块需要读取该流时，再手动开启。

冗余的第三次读取也一并移除，对应`bmi088-rs#1`，修改后`tofd`一次调用即可完成采样。
第三次读取仅节省0.3–0.9%CPU，落在上述测试噪声范围内。本次改动采纳它是出于其他考虑：对外发布的加速度数据，将直接用于四元数计算，而不是滞后约200微秒的另一次读取；同时读取失败只会在一处上报，而非两处。

采样频率是剩余可调节项，开销呈线性关系：`--imu-hz 50`可以将读取开销减半。
该参数保留为命令行flag，不写入配置项：由第一个实际消费方决定需要的采样率，不要提前预设一个无人使用的数值。

如果后续消费方需要低成本的100Hz采样，方案是使用FIFO。两颗芯片都自带FIFO，10组样本仅需一次I²C传输，替代原来20次。这是唯一能削减主要开销的方案。代价是帧解析、水位配置，以及最高100ms延迟；因此在消费方不存在的前提下，暂不实现。

## 备选的按需启停方案（现已不再使用，保留设计思路）
保留这部分内容，一是这个推导过程引出了开关方案；二是第1点本身属于bug，无论是否采用该方案都要修复。

### 1. 修正“是否有人订阅”判断逻辑（本身是bug）
`accept`会在读取请求字节之前，就为连接注册两路通道（tof/src/main.rs:612）。因此`receiver_count()`统计的是连接数，**不是真正的订阅意愿**：
请求`head_imu.stream`的客户端，会同时持有深度接收端；仅建立连接但不发送任何请求的客户端，两路接收端都会被计数。

需要将`subscribe()`调用移入`subscriber()`的分支匹配内部，只有识别到有效订阅方法时才创建接收端；函数入参改为传入两个Sender，而不是两个Receiver。
这项修改本身就有价值：一个没有请求任何数据的连接，不该被判定为需要深度数据。它也是后续所有按需启停逻辑的前置条件。

### 2. IMU线程：首个订阅者到来时启动，全部退订后关闭
IMU初始化开销很低：`open_imu`只是少量寄存器写入，无需固件上传、设备探测。线程可以等待IMU租约，有订阅时打开传感器、按imu_hz采样；订阅全部断开后关闭。同样可以节省4%CPU，无需操作员手动操作开关。

该方案没有落地：开关方案更早完成，代码量仅为前者的十分之一。但一旦出现消费方，该方案会更合适；否则开启该功能的机器人，在无人读取时依然持续承担4%CPU开销。
正确实现需要处理两个关键点：
- 订阅应答不能给出错误信息。`ImuStatus`初始状态为不可用：“尚未读取”，`head_imu.stream`的应答在第一次采样前就生成。冷启动时，该应答会被误判为“未安装BMI088”，但板卡明明装有该传感器。
因此处理器需要先唤醒线程，等待设备打开完成（有超时，几百毫秒），再返回设备存在/不存在的结果。（开关方案也存在同样问题，处理方式一致：`ImuStatus::off`单独标识，明确指向配置开关）
- 冷启动四元数需要收敛。Madgwick融合算法大约需要1秒稳定（tof/src/imu.rs:43）。现在开机就持续采样，订阅方拿到的是已经收敛的姿态；如果按需启动，订阅方拿到的姿态会仍在收敛。陀螺仪、加速度计原始数据不受影响。需要在`method::HEAD_IMU_STREAM`文档注明；等第一个真实消费方确认是否需要预热滤波，届时再加即可，现在无需提前猜测。

### 3. 不做测距启停控制，不管理测距单元
这是测量之前的备选方案，现已否决。

按需开启测距仅节省单核0.5%CPU。这就是`tof-sensor`线程维持激光开启、轮询并每秒发布15帧数据的开销（承接`idle-cpu.md`优化后的结果）。
启停测距本身开销很低：`start(hz)`/`stop()`各一次I²C事务（tof/src/sensor.rs:293、181）。但这要求在独占共享I²C总线的进程内维护状态机，恢复链路必须稳定，同时存在未验证硬件假设：停止再启动会不会重新上传固件。0.5%的收益不值得承担这些复杂度。

`robotd`里的theremin模块在开机就订阅深度流。它的深度读取器一次建立连接并保持（robotd/src/theremin.rs:237）。如果开启测距启停，只要该模块启用，激光就会持续打开。不做测距启停就没有这个锁定问题；而它提前连接的初衷——保证首次武装等待仅等待帧数据，不受影响。

支持激光启停仅剩一个理由：VCSEL激光器本身功耗。该功耗不属于CPU开销，`ps`无法观测。如果后续需要控制激光功耗，可以查阅VL53L8CX数据手册；若只是毫安级功耗，则维持现状，不做该功能。

## 为何不直接启停整个tofd单元
保留这部分，是因为它回答了本次问题的起源；其原因属于守护进程固有特性，并非单次测量结论。

- 上电初始化耗时数秒，且按进程独立执行。`Sensor::open`探测设备ID，然后上传ULD固件：I²C传输约90KB，400kHz速率下需要数秒（tof/src/sensor.rs:226），**每个进程启动测距前都要执行一次**。如果监控进程按需启动单元，会有数秒空白帧，`robotctl theremin`要等固件上传完毕才能进入武装状态。
- 没有可靠的“关闭”引用计数。多个客户端可以同时读取深度；客户端退出时停止单元，需要引用计数，且要能应对客户端被SIGKILL强制杀死。systemd对手动启动单元不提供这种引用计数。用`Ctrl-\`强制杀死监控进程，传感器会永远保持测距状态。
- 权限问题。monitor以robot组的operator用户运行；`systemctl start`需要root权限或polkit规则，授予该组管理单元权限。这属于新增安装依赖，旧版本预配的板卡会静默缺失该规则。
- 一个单元包含两个传感器。停止`tofd`会同时关闭头部IMU，而本文重点管理的正是头部IMU。

socket激活机制可以一次性解决权限与泄漏问题：`tofd.socket`接管`/run/tofd/tof.sock`，建立连接即触发进程启动，systemd管理生命周期。但它无法解决固件上传问题：每次会话首次连接都会上传固件，空闲退出后再次连接重复上传。
当我们目标是直接启停整个进程时，socket激活是合适方案；但它解决不了轮询开销问题，而实测后也证明，轮询本身不值得这样改造。

## 后续板卡验证项
1. 在启用开关的Duck机器人上执行`ps -L`，确认不存在head-imu线程。
2. 如果需要把第三次读取的开销精度提升到优于0.5个百分点：固定CPU调频，交替运行各模式重新跑基准测试。但当前决策不再依赖这个高精度数据。
3. 采集10分钟空闲SoC温度对比（开关开启前/后）。单核4%的负载很难在温度上体现。如实记录预期：本次优化目标是**停止无人使用的传感器采样**，不是降低发热。
