# WebRTC：会话、信令与控制通道
介绍手机、浏览器或服务端程序如何通过WebRTC对机器人进行控制与状态观测。`architecture.md`第5节规定了需求；本文档负责说明实现机制。

适用范围为**本地信令**：下文所有组件均运行在机器人端，可在局域网内独立工作，无需后端服务。从局域网外部访问机器人采用相同架构，仅在前端增加代理（第7节）——该代理并非优先开发项，因为本地场景是所有其他场景的基准参照。

## 0. 状态：硬件可运行
Radxa Zero 3W开发板将视频测试源经由硬件编码器推流至局域网内浏览器，浏览器同时接收控制数据通道。2026-08-25完成端到端验证：

| 模块 | 说明 |
| ---- | ---- |
| 信令 | mediad进程内运行信令服务；生产者注册，消费者列举并启动会话 |
| 视频 | mpph264enc → webrtcsink → 浏览器，协商参数`profile-level-id=42e01f`，即受限基线（Constrained Baseline），这正是第2节的核心目标 |
| 通道捆绑 | `a=group:BUNDLE video0 application1`、`a=sctp-port:5000`，媒体流与数据流复用同一条传输链路 |
| 数据通道 | 控制指令可送达对端 |

有两项功能此前从未调试，首次尝试就触发故障，在此记录：这类故障是本设计模式下典型问题，并非偶发bug。

1. 在GStreamer信号回调线程内调用`tokio::spawn`会直接导致进程终止。该线程不属于Tokio运行时；C闭包内发生panic时，无法执行栈展开。系统日志显示：线程触发**不可栈展开panic**，调用栈经由`g_closure_invoke`，但不包含根因信息。所有回调处理函数内**禁止panic**，详见`mediad::pipeline`头文件。
2. 浏览器打开`file://`本地页面时，客户端无法连接信令端口。Chrome的私有网络访问（Private Network Access）策略会阻止**不透明源**访问私有IP；将页面通过`http://localhost`提供访问即可修复。

若编解码器协商失败，系统仅输出警告而非直接报错。从预编码H.264切换为原始视频（第2节）后，编码器被移入webrtcsink，在能力探测阶段要求`profile=constrained-baseline`；但mpph264enc的Pad模板并未声明该参数，导致SDP提议中H.264消失，协商改用VP8，最终会话中断。所有表象都指向别处：可见报错来自上游四级之外的videorate组件，提示NV12格式问题。该问题需要插件v3及以上版本。这也是mediad把GStreamer调试日志与流水线总线消息接入系统日志的原因——若无日志桥接，上述问题完全无法排查。

### 摄像头：帧丢失35%的两个独立根因
头部摄像头通过硬件编码器输出29.3fps视频。达到该帧率需要两个互不相关的修复项；难点在于单独修改任意一项，帧率都不会变化，因此两项修改单独测试时都看似无效。

**捕获缓冲区池深度**：rkisp未实现`V4L2_CID_MIN_BUFFERS_FOR_CAPTURE`，因此`gst_v4l2_object_decide_allocation`从0计算`own_min`，默认分配2个缓冲区。缓冲区数量是断崖式影响而非线性变化：主链路用`v4l2-ctl --stream-mmap=N`测试，2缓冲区时帧率19.7fps，≥3缓冲区时可达29.2fps。
调高缓冲区池最小值需要同时满足两点：ALLOCATION查询中携带GstVideoMeta（否则`can_share_own_pool=false`，不会读取查询中的最小缓冲区参数）；并且首个缓冲区池的最小值非0。下游组件提议缓冲区池时会更新参数，丢失+2缓冲区的补偿；`GstVideoEncoder::propose_allocation`就会触发该行为。

**像素格式**：rkisp同时提供单平面格式与非连续双平面NM12。两者在GStreamer中均映射为NV12，v4l2src优先选择多平面NM12；但无论缓冲区池多大，该格式都无法跑满帧率：

| 能力 | 2缓冲区 | ≥4缓冲区 |
| ---- | ---- | ---- |
| NV12（选用NM12） | 19.5 fps | 19.6 fps |
| UYVY（单平面） | 19.7 fps | 29.3 fps |

mpph264enc的接收Pad支持UYVY，可在RGA硬件单元完成格式转换，4:2:2转4:2:0不占用CPU。

通过实测排除了其他疑似因素（而非凭逻辑推断）：同一节点下`v4l2-ctl`两种格式均可跑到29.2fps；传感器子设备上报1/30s帧间隔；驱动未实现S_PARM；mpph264enc硬编码720p最高可达130fps；无约束条件下v4l2src偏好的DMABuf能力，并不是无约束下高速的原因。

**方法论教训（代价高于所有前述问题）**。曾使用4种不同指标当作捕获帧率，但全部不准确：
- rkvenc中断统计的是编码器消费的帧，位于webrtcsink队列与转换器bin内仅丢帧的videorate之后；
- v4l2src检测丢帧依靠驱动序列号间隙，当源端只是变慢时不会上报；
- tee原始分支的计数器，位于一个刻意设置的单缓冲区泄漏队列之后；
- `/dev/video1`是ISP自环通路，并非守护进程使用的主通路。

mediad现在在tee节点前采集Pad帧率，这是唯一在驱动与采集点之间不存在丢帧环节的位置。

本次暴露两个尚未修复的问题：`rtpgccbwe`占用约40%单核CPU；同时尽管日志桥将GStreamer的INFO级别日志映射为`tracing::info!`，GStreamer的INFO日志仍然无法写入系统日志，因此很多问题只能靠低效方式定位。

尚未测试场景：**所有经由桥接代理的链路**。

## 画质档位选择：为何只用单一配置项，而非四项独立参数
视频流参数（摄像头/测试图、分辨率、帧率、码率）在板级配置文件`/etc/robot/robotd.toml`的`[media]`段，robotd守护进程原本就会读取该文件。
`sudo robotctl configure`命令用于编辑配置，并自动提示执行`systemctl restart mediad`；mediad仅在启动时读取一次配置，与本项目其他守护进程一致。

使用单个画质档位字段：`1080p30`、`720p30`、`720p15`、`360p30`，而非分开配置宽、高、帧率。
宽高帧率三者不能独立修改：采集链路无法生成的组合会直接导致流水线启动失败，连带控制通道一起失效（数据通道与视频轨道捆绑，见第2节）。所有档位均为传感器原生16:9宽高比，因此“降低分辨率”不会悄悄裁剪画面。码率是唯一可独立配置的参数；如不设置，则跟随档位取值：720p30默认2Mb/s，本文所有测试均采用该码率。

在增加该配置段之前，这些参数是`mediad.service`里的`ExecStart`启动参数。发布安装程序会重写该systemd单元文件，修改参数需要使用systemd覆盖配置（drop-in）；该机制用于硬件接线不同的板子，**不是用来调整画面模糊问题**。

## 拥塞控制同样是CPU相关配置项
`[media] congestion_control`，可选gcc、自研算法或禁用，对应webrtcsink自身的拥塞控制属性，为显式配置而非继承。gcc是该组件默认值，填写gcc不会改变行为；该配置的意义是：上游库修改默认值时，不会自动变更所有机器人的发送码率。

拥塞控制是进程内最大的单核CPU消耗项。单板、单个对端连接时各线程CPU占用（单核占比）：

| 线程 | CPU占比（单核） |
| ---- | ---- |
| rtpgccbwe1:src | 7.6% |
| queue1:src | 6.0% |
| mpph264enc2:src | 5.0% |
| … | … |
| v4l2src0:src | 0.3% |
| queue3:src（原始tee分支） | 0.3% |

总CPU占用约单核25%，重点在于负载分布：采集与原始分支帧拷贝（仅这两项负载随像素数量线性增长）合计仅0.6%。其余全部是数据包处理，负载随码率变化。
这就是调低画质档位不一定降低CPU的原因：链路带宽充足时，拥塞估计器会把360p码率拉高至接近720p水平，把带宽用于提升单像素画质。

设置为`disabled`会删除rtpgccbwe线程，代价是失去码率自适应能力。而webrtcsink传入原始视频而非预编码H.264（第1节）的核心目的就是自适应：链路恶化时，依靠自适应维持画面，避免卡顿。同时禁用拥塞控制后，码率参数将严格生效，不再是初始参考值。

目前**仅720p30档位完成实测**。传感器固定工作在1080p@30fps模式，由ISP做降采样；1080p30无需缩放。但尚未验证：像素量提升至2.25倍时，采集链路与编码器能否稳定维持30fps。如果档位无法跑满帧率，会自动降速，**不属于启动失败**。

## 1. 本方案不采用的组件
未使用`webrtcbin`。mediad使用`gst-plugins-rs`中的`webrtcsink`，这也是本文档能简化的根本原因：webrtcsink自带信令协议、会话模型、按消费者独立管理编码器；因此设计重心是控制接口，而非媒体传输管道。

如果选用webrtcbin，则需要自行实现这三部分。webrtcbin在Debian源内可用，而webrtcsink不在（`media-bringup.md`介绍插件编译打包方式），这是选择webrtcbin唯一的理由；但该劣势被webrtcsink自带协议抵消——远程桥接代理正是转发这套协议（第7节）。

## 2. 一个会话，四条流
> 对端（浏览器 / 手机 / 服务端程序）
> ├── 视频轨道　摄像头，硬件H.264编码（mpph264enc，受限基线）
> ├── 音频轨道　麦克风；双向，用于远程临场
> ├── 数据通道“control”　可靠有序　→ 机器人API（第5节）
> └── 数据通道“teleop”　不可靠无序 → 操控输入与高频遥测

使用两条独立数据通道，理由见`architecture.md`5.2节：重传80ms前的摇杆指令弊大于利。因此遥控通道设置`maxRetransmits:0`，永远采用最新数据包。

第一版仅启用control通道。teleop遥控并非近期优先级，去掉它不只是延期实现，第6节会说明移除带来的简化。

webrtcsink接收Pad上送入预编码H.264，编码器不参与SDP协商。硬件上已验证；四项编码器参数属于业务决策而非默认值，详见`media-bringup.md`。

流水线在编码器前对原始NV12帧做分流，该设计是有意为之：
```
                              ┌─ queue ─ mpph264enc ─ h264parse ─ webrtcsink
采集 ─ NV12 ─ capsfilter ─ tee
                              └─ queue(泄漏，1缓冲区) ─ appsink ─ 按需获取帧
```
5.3节要求服务端程序按需获取帧：“每隔一两秒获取一帧图像+状态数据包”，不需要解码30fps H.264流；`architecture.md`第2节要求感知计算靠近传感器，提取特征，而不是把像素全部传给robotd。两者都需要原始像素；如果从编码后分支取帧，就要对刚编码完成的视频做解码。

全程使用NV12格式：rkisp输出NV12，mpph264enc也接收NV12，全程无格式转换。每个分支拥有独立队列：如果没有队列，tee会用单线程驱动两路分支，慢速读取端会阻塞视频主轨道。原始分支队列设为**泄漏模式，深度1**，只保留最新快照，符合`architecture.md`第2节要求，不堆积旧帧。读取端阻塞只会丢原始分支帧，不会影响编码器。

appsink仅在读取端发起请求时拷贝帧。该分支的读取端合计每秒最多2帧：自动曝光每500ms测光一帧；目标检测启用时每秒2帧。720p30单帧大小1.84MB。如果持续采集全部30帧，每机器人开机就持续产生55MB/s内存拷贝、每秒30次1.8MB内存分配，大量帧无人读取。所有缓冲区依然送到appsink，未读取直接丢弃；未被请求的帧仅产生轻量加载开销。

请求响应采用**下一帧**而非最近已交付帧。直接返回缓存旧帧开销更低，但会把读取端轮询周期带入感知闭环：曝光回路基于半秒前的亮度做调节，会造成震荡。读取端阻塞等待新帧并带超时；摄像头停止采集时，会统一走“无可用帧”分支。

该分流分支从一开始就内置，而不是按需动态添加：向正在运行的流水线插入tee节点，难度远高于预先部署好tee。

## 3. mediad内置信令服务
webrtcsink支持`run-signalling-server`，配套`signalling-server-host`、`signalling-server-port`（gst-plugins-rs 0.15.3）。信令服务运行在mediad进程内部，无需独立二进制程序编译、分发、守护。这点很关键：我们交付的插件是.so库，而gst-webrtc-signalling-server是同仓库下独立Rust可执行文件。不单独部署它是实质性简化，不是临时偷懒方案。

webrtcsink内置信令客户端默认地址`ws://127.0.0.1:8443`，连接本进程启动的信令服务。局域网客户端直接连接同一服务：`mediad/webclient/index.html`就是客户端，单文件无需编译，手动实现协议，不依赖gst-plugins-rs的JS库，开箱即用。页面后续规划（机器人托管页面、机器人发现、控制界面）见`webrtc-console.md`。

绑定地址是主动配置项，不是默认值。仅绑定回环地址会导致局域网设备无法访问，所有会话必须走桥接代理，违背本地模式设计初衷。因此监听所有网卡；第4节介绍对应的访问权限问题。

## 4. 鉴权：机器人端不做鉴权，本地与远程场景均适用该逻辑
第一版不设置访问闸门。只要能连上信令服务，对端即可启动会话、控制机器人、查看摄像头画面。这是**主动设计决策**，不是遗漏。

当前阶段可用性优先级高于安全加固，取舍很明确。机器人配对PIN固定为`000000`；所有机器人共用同一PIN，无法完成身份认证。若WebRTC层面强制校验PIN，每次首次连接都会增加一步操作，但完全不提升安全性。增加首次连接的操作负担，却没有安全收益。

代价直白说明，避免用户踩坑：同一局域网内任何人都可以访问机器人与摄像头。在实验台、办公室环境没问题；家庭环境不可直接使用，量产前需要重新评估。

**鉴权实际放在桥接代理层，该机制已就绪**
远程访问路径同样不需要机器人本地鉴权，连接到达机器人前，两端都完成鉴权：
1. 客户端通过OAuth向中继服务认证，服务仅展示该账号名下机器人。能够访问路由到指定机器人的桥接部分，本身就是身份凭证。
2. 机器人向外认证：中继持有账号token，使用token连接服务（第7节），证明机器人归属该账号。

服务匹配两个已经完成鉴权的通信方；经由桥接建立的会话，经过双重授权。如果再叠加`system.authenticate`鉴权，就是对已经解决的问题重复验证，且安全性更弱——共享PIN的可信度低于账号token。

这意味着信任边界发生转移，而不是消失：机器人不再独立校验身份，机器人与账号的绑定关系成为信任核心，该绑定保存在云端服务而非机器人本地。这是合理的方案，只有服务端能维护该绑定；但这是外部依赖，并非无安全机制。

唯一不受该模型覆盖的场景：通过端口转发，直接把机器人信令端口暴露到公网，**不经过桥接代理**。此时没有桥接完成鉴权，第4节局域网安全假设失效，访问者不再局限于内网人员。这属于部署错误，不是设计缺陷；机器人本身不会感知该风险。

### 预留扩展接口（暂不启用）
`system.authenticate`：BLE协议已使用该接口，API版本v4新增。控制通道可先执行该方法，认证通过前拒绝其他接口调用；PIN通过unix socket从configd读取，**不在待认证的控制通道内传输**。

在此记录仅作为方案储备，暂无开发计划。适用场景很有限：桥接链路已有更强鉴权，增加该接口无收益；局域网场景每一次连接增加一步校验，仅证明对方读到机器人机身上印的PIN码。如果后续需要启用，改造成本很低：第5节路由表已经需要维护“传输通道可访问哪些接口”；“认证前可访问接口”是同一张表的子集，不需要新增机制。

# 5. 控制通道：通往现有API的管道
控制通道上的消息帧采用JSON-RPC 2.0协议，每行一个JSON对象。该协议已在`duck-ipc-proto`中定义，`robotctl`与`btd`均使用这套协议。本方案没有新增自定义协议：`mediad`将调用路由至对应服务的Unix域套接字，并把返回结果回传给客户端。

`btd`是已验证的先例，将作为共用实现模板：

| btd现有模块 | mediad所需功能 |
| ---- | ---- |
| `route.rs` — 定义允许转发的调用、负责应答的套接字、承载消息的通道 | 复用同一张路由表，仅允许访问的接口子集不同 |
| `session.rs` — `system.authenticate`鉴权闸门 | 复用同一鉴权闸门 |
| `upstream.rs` — 连接套接字，所有请求增加超时控制 | 完全复用 |
| `framing.rs` — BLE MTU分片处理 | 无需；SCTP自带帧封装 |

四个文件中有三个与传输层无关，仅一个和传输层绑定。把路由表抽离为可被两种传输方式共用的组件，通过参数限定该传输可访问的接口子集。

需要保留的核心特性不是代码本身，而是**穷尽式匹配**。`route.rs`明确体现该设计：若在`proto::Call`新增一个变体，文件会直接编译失败。这样就不会出现有人新增接口，但忘记修改路由表，导致新方法无法通过无线通道调用的情况。如果使用`_ => None`通配符，新增接口会被静默拒绝；第一个现象就是客户端发现某个功能不可用，却很难定位根源。该保证必须对每一种传输通道生效，否则WebRTC就会成为安全漏洞。

### WebRTC可访问的接口范围，以及为何不等同于BLE的子集
BLE的接口子集范围很窄：蓝牙传输速率低，且数米范围内任何人都可接入。WebRTC不受这两个限制，因此可访问更多接口，但**并非全部接口**，以下两类接口禁止访问：
1. `system.pairingPin`与`system.setPairingPin`。并非因为这两个接口会危害WebRTC传输（第4节本就未做本地鉴权），而是它们用于对**另一套传输通道**做授权。局域网内的对端如果能修改配对PIN码，就可以让手机无法通过BLE接入，而BLE是系统的故障恢复通道。所有网络传输通道都禁止访问PIN相关接口，这和BLE本身不能路由PIN接口是同一套规则。
2. `update.*`修改类接口。**仅现阶段限制**，原因和PIN码不同：执行升级会重启`mediad`，导致客户端正在查看进度的会话断开。后续会支持；第8节介绍所需改造。

还有一类接口需要在此说明（而不只是写在路由表里）：`account.*`，用于将机器人绑定到Hugging Face账号。这是本传输通道支持的第一类状态修改接口，控制台就是机器人登录账号的入口。它也是唯一**会话结束后效果依然保留**的接口（账号绑定）。`remote-access-design.md`第2.6节阐述了设计依据与三项约束，`mediad::route`内有简要版本。

### 应答与请求不做关联（刻意设计）
`btd`直接转发套接字输出的全部内容，不做解析，并且有对应的测试用例保证该行为：订阅是长连接上持续推送的通知流，每一条通知都必须送达客户端。如果把应答和请求做关联，就会破坏订阅机制。`mediad`沿用该规则：新增接口时，`mediad`不需要为每个接口单独编写处理逻辑；管道保持简单透传，接口定义只在`duck-ipc-proto`一处维护。

**通道（lane）**的概念同样可以复用，这点很容易被忽略。每个守护进程在一条连接上同一时间只处理一个请求，因此同一条连接上先调用`update.subscribe`再发送其他请求会发生阻塞，`app-path-design.md`第7节记录了这个bug。单条数据通道就是一条有序流，存在完全相同的风险。`btd`的解决方案可直接复用：根据接口方法路由到独立通道对应的套接字，分别回传各个套接字的输出，**不做请求应答关联**。

# 6. 优先实现仅控制通道，以及后续增加遥操作通道的代价
`intents.rs`将每个控制意图存入`ArcSwap`，采用**最后写入者生效**策略。当前该机制是可靠的：所有写入都经由Unix套接字，不会出现后发消息先抵达的情况。

可靠有序的数据通道可维持该特性。SCTP在该模式下保证按序投递，因此通过控制通道下发的意图依然满足`intents.rs`依赖的时序约束。因此优先只启用一条通道，不是为了临时妥协、遗留技术债，而是第一版根本不需要解决时序乱序问题。

### 带来的代价（提前说明，避免意外）
**队头阻塞**：可靠通道一旦丢包，该包之后所有数据包都会被阻塞，包括控制RPC调用。链路质量差时，现象是所有操作全部卡住，而不是摇杆指令陈旧。在较低指令速率下，通过控制通道遥控机器人尚可；速率越高、丢包越严重，延迟问题越明显。这正是`architecture.md`第5.2节规定需要第二条通道的原因；遇到“链路差导致机器人操控延迟”的问题，解决方案是启用遥操作通道，而不是调参优化。

### 遥操作通道上线后，必须增加序列号
`maxRetransmits:0`模式下的SCTP会出现报文乱序。80ms前的摇杆指令有可能晚于新指令到达，并且因为最后写入者生效，机器人会执行陈旧指令，且系统不会上报任何异常。这不是罕见的竞态问题，而是该传输模式**刻意选择的正常行为**。

因此遥操作通道的每个帧携带**单流单调递增序列号**；接收端丢弃序列号不大于上一条已执行指令的报文。该逻辑属于传输层特性，放在`mediad`而非`robotd`中实现。`robotd`持续接收时序可信的意图，保证`intents.rs`保持简单。

需要在通道开发前就记录这个问题：该故障静默发生，表象像是参数调优不佳，而非程序bug；如果在设计阶段就内置序列号，修复成本很低；如果等到出现陈旧指令问题再排查，处理会很麻烦。

无论是否启用遥操作通道，**安全看门狗无需改动**：`safety.gate(command, twist_age)`本身基于指令时间判断，一旦链路断开，机器人会自动停机，无需新增代码。

# 7. 访问局域网外的机器人
远程访问方案是**本地信令服务器的桥接代理**，不是另一套独立设计。一个中继进程向外连接到会合服务，将相同协议代理转发至`ws://127.0.0.1:8443`。机器人的信令服务、会话模型、鉴权机制与控制通道均保持不变；DTLS-SRTP保证媒体流即使经过中继，依然端到端加密，需要明确告知客户端。

该架构具备两个核心特性，也是选择该方案的理由：
1. **本地模式不依赖桥接服务**。会合服务宕机，局域网客户端仍然可以连接。`architecture.md`不变性约束1（本地恢复能力独立可用）同样适用于媒体流。
2. **桥接代理不自定义协议**。消息封装沿用GST信令协议，局域网客户端原生支持；SDP、ICE等载荷透传，代理不解析。这就是选用`webrtcsink`而非`webrtcbin`的实际收益。

但桥接代理**不是纯粹的透传中继**（早期文档曾误以为是纯中继）。`reachy_mini`的会合服务通过HTTP承载报文：上行SSE，下行POST，而非WebSocket；对端ID与会话ID是逐跳生成。因此桥接代理会重写消息封装，并维护双向会话表，本质是载荷不透明的协议转换器。`remote-access-design.md`第3.2节对比了两端协议。

鉴权在桥接层完成，机器人无需本地鉴权。中继进程携带账号token向外建立连接；服务仅向客户端展示该账号名下的机器人。经由桥接建立会话，在到达机器人前两端均完成鉴权。信任模型见第4节。

一个有用的特性：中继是机器人侧进程，连接回环地址。机器人可以根据源地址区分连接来自桥接代理还是局域网客户端，虽然当前没有利用该差异做逻辑处理。后续如需基于来源做差异化策略，架构上没有限制。

`reachy_mini`已在Hugging Face Space上运行这套架构：机器人以生产者身份注册，Space通过心跳维持TTL租约。本地模式现已可用，本节遗留的两个问题（是否复用该会合服务、机器人如何绑定账号）不再悬而未决，由`remote-access-design.md`定义。账号认证采用Hugging Face OAuth设备码流程，而非`reachy_mini`使用的重定向流程（第2.1节说明原因）。

### 桥接开发者可用的信令协议
取自gst-plugins-rs 0.15.3，`net/webrtc/protocol`；线上报文为带类型标签的JSON，采用驼峰命名。

| 对端 → 服务端 | 服务端 → 对端 |
| ---- | ---- |
| `setPeerStatus (roles, meta, peerId)` | `welcome (peerId)` |
| `startSession (peerId, optional offer)` | `sessionStarted (peerId, sessionId)` |
| `endSession (sessionId)` | `startSession`、`endSession` |
| `peer (SDP offer/answer, or ice)` | `peer`、`error (details)` |
| `list`、`listConsumers` | `list (producers)`、`listConsumers (consumers)` |

角色分为生产者、监听者、消费者。机器人作为生产者；`meta`为自由格式JSON，用于携带机器人身份信息。

# 8. 通过WebRTC升级机器人：暂不支持，及所需改造
升级接口不在第一版允许访问的接口子集内，属于**延后实现，不是永久禁止**。后续计划支持手机通过WebRTC升级机器人，本节说明前置条件，而非阐述为什么不能做。

当前难点：执行升级会重启`mediad`，直接中断客户端正在监控进度的会话。`update-over-ble.md`记录过一次“启动升级后进度静默中断”造成的故障；升级中途会话消失属于同类问题。因此第一版不开放`update.*`修改类接口，BLE作为升级时能在重启后保持连通的传输通道。只读类`update.*`接口从一开始就开放：远程会话读取版本、升级历史有实用价值，且无副作用。

要支持修改类升级接口，需要两处小规模、明确的改动：
1. **客户端需要支持重连**。协议本身已经具备能力：升级进度以JSON-RPC通知推送，`duck-ipc-proto`文档专门定义该机制，客户端在升级中断重连后可重新订阅，继续接收进度。改动点在客户端实现重连与重新订阅，不需要修改线上协议。
2. **`RobotRemoteSessionActive`标识需要细化**。`updater/src/preflight.rs::check_no_remote_session`会在存在远程会话时拒绝升级。当会话是旁观用户时该逻辑正确（用户正在远程临场，不应在不知情下重启机器人）；但**当会话本身就是发起升级的请求方时，该判断错误**。目前没有代码设置该标识，因此可以提前设计区分逻辑，而不是后期补丁改造：校验逻辑需要知道本次升级请求，是否来自即将被断开的这个会话。

现在记录这点非常必要，因为该标识尚未被赋值。一旦`mediad`如实上报会话状态，通过WebRTC发起的升级会被自身拒绝，表象会被误认为升级模块bug，而不是缺少该区分逻辑。

# 9. 权限控制：本功能打破的前提假设，已记录暂不处理
`intents.rs`描述其存储槽：“实际为单写入者，因此最后写入者生效符合预期”。单个游戏手柄操控时该假设成立。一旦手柄和远程对端同时下发操控指令，假设失效。故障现象不是两者争夺控制权，而是两个50Hz写入流交替写入同一个存储槽，最终机器人不执行任何一方指令。

本版本**不解决该冲突**。记录该问题，方便后续出现机器人行为异常时有文档可查；并且控制权令牌在新增第二种传输通道前设计，成本更低。`architecture.md`第6节定义需求：优先级、控制权移交，本地物理操控可抢占远程操控；该需求放在M6里程碑。

后续低成本方案：**单写入令牌**。同一时刻仅一个对端拥有写入意图的权限，其余为观察者；控制权移交显式触发。该方案远小于第6节完整仲裁逻辑，但可以消除指令交替写入导致的乱码行为（而不只是解决“谁优先级更高”）。优先级规则（本地无需询问直接抢占远程）可以后续叠加在这套令牌机制之上。

在实现之前，本节的意义：让大家知道**双操控源并发是已知缺陷，不是未知bug**；故障首要现象是机器人忽略双方输入，而不是错误执行其中一方指令。

# 10. mediad编译构建说明
`gstreamer-rs`相关crate依赖pkg-config，交叉编译时开发机上必须具备目标平台的头文件、`.pc`文件以及共享库。`cargo board`可在macOS上借助`cargo-zigbuild`完成交叉编译。之前用于提供C依赖的多架构脚本描述：“这是引入该例外的代价，新增依赖前需要阅读”。本项目是第二个，且复杂度高得多，直接替换了旧脚本。Ubuntu多架构源可以提供libudev，但无法正确提供GStreamer：会返回Ubuntu版本库，而机器人运行Debian trixie版本。

`scripts/cross-sysroot.sh`将机器人对应的Debian软件包解压到sysroot。经验证：整个工作区可基于该sysroot交叉编译，`gstreamer`、`gstreamer-app`、`gstreamer-webrtc`均解析到1.26.2版本，与板载版本一致。

修改该脚本前需要了解三点：
1. 它服务整个工作区，不只是`mediad`。`PKG_CONFIG_LIBDIR`是**替换**pkg-config搜索路径，而非追加。如果sysroot只包含GStreamer，会破坏`padd`（其gilrs依赖libudev），故障发生在`libudev-sys`内部，和媒体模块无关。采用替换模式仍是正确选择：`PKG_CONFIG_PATH`是追加主机路径，容易让pkg-config读取macOS本地库，生成无法在机器人运行的二进制。
2. 软件包列表为手动指定，而非自动依赖解析。从基础包递归解析Debian依赖会拉取543个包：`libgstreamer-plugins-bad1.0-dev`声明所有可选后端的开发包，依赖链包含Qt、Vulkan、OpenEXR。实际仅需19个包即可满足构建需求。
3. 仅`-dev`开发包不足以完成链接。`-dev`包内`libfoo.so`只是软链接，指向运行时包中的`libfoo.so.N`，因此`-lfoo`链接需要两者。仅出现在`Requires.private`中的库，只需要`-dev`包。

替代方案：在arm64构建机上编译mediad，类似`media-bringup.md`中的插件构建方式。该方案被否决，因为会把守护进程拆成两套构建流程，开发者无法在笔记本编译mediad。而这个crate需要大量真机迭代，该取舍并不合适。

### media.video：画面几何参数
包含宽、高、安装旋转角度，以及相机内参。接收端需要内参，才能将像素坐标转换为空间方向。没有内参，单目重建结果尺度不确定，角度存在偏差；SLAM、视觉里程计、测距功能都依赖内参。

包含4个数值与1个标记：`fx`、`fy`、`cx`、`cy`、`calibrated`。参数描述发送出的原始帧（未旋转，机器人端不会旋转像素）；接收端如果做画面旋转，需要同步旋转内参，交换`cx`与`cy`。标记不是装饰：
- `false`：使用IMX219模组设计参数（3.04mm焦距，像素间距1.12µm，主点假设在中心，无畸变模型），误差百分之几，足够做室内建图；
- `true`：实测标定参数，存储在`[media.intrinsics]`；或者alpha系列相机镜头一体模组，使用`robotd-params`提供的同批次标定结果。需要高精度测量的接收端，可以读取该标记判断是否为实测标定。

几何参数未知时，该键直接省略，而不是填入错误数值。例如机器人推送测试图，或是`media-ctl`未配置传感器模式：传感器工作在3280×2464开机模式，视场覆盖整个感光阵列，不是1920×1080裁剪区域，所有内参会有约1.7倍偏差。`mediad::camera`包含相关计算与模式表，其中有一个关键点：从传感器读取720p画面只会缩小视场至27°，并不会降低任何开销。

# 11. 所有线上报文都应附带事件时间戳（待实现需求）
当前这套传输通道所有报文**源头不带时间戳**。帧到达时才被接收端拿到，`robot.state`通知也是如此。接收端想知道机器人采集图像或传感器触发的时刻，只能依赖自身时钟。跨大陆中继场景下，时钟偏差等于网络传输延迟。

该方式用于实时观看画面操控机器人尚可，但所有远程高级应用都不适合。SLAM是典型例子：不带采集时间戳的视频流可以跑单目SLAM；一旦需要视觉惯性融合（机器人自带50Hz IMU，在同一控制通道传输），两组数据只能靠猜测对齐。接收端添加的时间戳记录的是网络到达时间，不是机器人采集时刻。

分为两个独立问题：
1. **媒体流**：RTP时间戳是相对随机偏移值，仅用于排序，不代表真实墙上时钟时间。解决方案是`abs-capture-time` RTP头部扩展，每个数据包携带采集的绝对时钟，接收端用来将视频和其他传感器数据对齐。首要验证点：`webrtcsink`是否支持协商该扩展，浏览器与aiortc能否暴露该扩展字段。如果接收侧无法读取，头部扩展没有价值。
2. **控制通道**：由我方实现，成本较低。所有描述瞬时事件的通知消息，增加单调计数器，加上系统启动纪元，实现跨进程时间比对。代价是每条消息增加一个字段，并且需要统一时钟源；媒体流帧时间戳也必须使用同一时钟，否则两组数据依然无法对齐。

暂未开发，并且不作为远程访问功能的一部分启动：该改动会改变所有通知消息结构，需要单独评审、独立版本号升级，不依附传输通道迭代。`remote-access-design.md`第9节标记为待解决项。

# 12. 延后实现的功能及原因
1. **服务端程序WebSocket接口**（`architecture.md`第5.3节）。复用JSON-RPC，无媒体协议栈，`get_frame`返回JPEG图像。在第5节路由实现后只需几十行代码，方便实现“大模型控制机器人”场景。但属于第二套传输通道，优先保证WebRTC主通道可用。
2. **遥操作数据通道**。非近期优先级；第6节说明延后带来的简化、当前代价，以及后续需要的序列号机制。
3. **多对端视频**。同一时间仅支持一路媒体会话，外加仅控制的客户端。联播（simulcast）、一次编码多路分发是独立大型项目。
4. **会话授权与推流指示灯**。`architecture.md`第7节要求每个会话显式授权、可视化指示灯。现在实现成本低，后期改造代价高。需要可软件控制的LED硬件，目前硬件尚未就绪。
5. **TURN服务**。纯局域网场景不需要。桥接代理场景需要，会占用大量带宽；该决策由会合服务负责，不在本模块。
