# 手机端应用 —— 构建原理
状态：已构建 · 日期：2026-09-17 · 负责人：pierre

用户端应用能力：将机器人直立、接入WiFi网络、固件升级、账号登录、遥控移动、查看设备健康状态，并下发指令执行内置任务。本文说明应用的开发技术栈、复用现有另一款机器人应用的部分能力，以及机器人侧尚待补齐的配套能力。

代码仓库位于 `pollen-robotics/microduck-app`，存放应用代码与工程化相关内容：编译、签名、打包安装到手机。本文为设计思路文档：说明应用架构设计的原因，以及各项设计取舍带来的代价。

本文配套 `app-path-design.md`，后者定义机器人侧能力：GATT接口、路由表、通道、配对、身份标识以及所有相关待解决问题。两处文档存在交集时，以机器人侧文档为准，本文仅做引用。`remote-webrtc.md` 定义另一套传输通道，§1.2 为两份文档的边界。

## 1. API 即规范，应用作为客户端
`btd/src/route.rs` 定义手机端可调用的全部接口；`duckctl.md` 是本应用最接近功能规格书的文档：文档内每条命令，都可以由应用通过同一蓝牙链路发起，并收到相同格式应答。

| 页面 | 可调用接口 |
| ---- | ---- |
| 选择机器人 | 广播包（设备名称、IPv4地址），随后执行 hello 握手与 `system.authenticate` 身份认证 |
| 机器人信息页 | `system.info`、`robot.health`、`system.services`、`system.setName`、`system.reboot`、`robot.init`、`robot.enable` |
| 遥控驾驶 | WebRTC：视频流、`robot.move`、`robot.subscribe` |
| 任务控制 | `robot.skills`、`robot.do`、`robot.policies`、`robot.loadPolicy`、`policy.check`、`policy.search`、`policy.fetch`、`policy.install` |
| WiFi配置 | `net.status`、`net.scan`、`net.connect`、`net.forget` |
| 固件更新 | `update.check`、`update.apply`、`update.subscribe`、`update.status`、`update.listInstalled`、`update.log`、`update.rollback`、`update.select` |
| 日志查看 | `system.logs` |
| 账号 | `account.login`、`account.status`、`account.logout` |

后续如果需要新增未路由的接口，只需修改一行 `route.rs`，再判断该接口是否适合走蓝牙链路。这正是§3.2设计要实现的能力。应用已经四次验证该机制：`update.rollback`、`update.select`，之后是 `robot.init`、`robot.enable`。这几个接口原本被禁止，实际使用中发现禁止策略带来的负面影响超出当初的预判，因此开放。

### 1.1 它是机器人交互界面，而非简易设置工具
最初路由接口仅包含WiFi、升级、健康状态与设备名称。现在已覆盖用户操作Duck机器人的绝大多数场景。`route.rs` 的设计逻辑：蓝牙通信距离约10米，操作手机的人就在机器人旁边；并且蓝牙绑定需要PIN码校验。因此BLE最适合确认**谁正在操作机器人**，也是该文件中大多数接口访问限制的判断依据。

因此下文整套机制并非过度设计。简易设置工具只需要单次调用+加载转圈动画；而完整交互界面不能这么做。

**不通过蓝牙传输的内容**：持续控制指令、所有流式数据（`robot.move`、`robot.subscribe`、`tof.stream`、`pad.input`）、配对PIN码、`update.pin`、`update.resetToGolden`，以及两类故障会造成机器人倾倒的接口：`robot.relax`、`robot.rebootMotors`。
第一组交给另一套传输通道处理；其余仅允许机器人本地终端操作。

### 1.2 两套传输通道，不存在竞争关系
除驾驶之外，上面所有功能均走BLE。选用BLE作为应用主通道的原因见机器人侧文档§2.2：**无网络环境也能修改配置**。开发板在新环境上电，找不到已知WiFi，局域网完全无法访问。如果应用必须依赖局域网修改配置，就无法修复“机器人连不上局域网”这个根源问题。

驾驶功能本身依赖网络，通过蓝牙调用 `net.status` 获取可使用的网络地址。两套通道协同工作：可靠的BLE通道，告知客户端如何接入高速的WebRTC通道。机器人本地控制台也不是竞品，控制台同样需要网络地址，而配置网络恰恰是手机应用的作用。

## 2. reachy_mini_mobile_app 是参考范例，不是基础工程
Pollen 为 Reachy Mini 发布了基于 Tauri 2 的应用：React19、MUI、tauri-plugin-blec，支持 TestFlight 与谷歌内部测试渠道。该应用通过BLE完成机器人配网，其余操作走局域网与Hugging Face。

它的BLE协议是一套独立方言：4个特征值，命令以字符串形式下发，依靠子串匹配解析应答（`ERROR:`、`OK:`，`ECHO:`代表固件版本过低不支持该指令）。其源码自述为一次性测试接口。并且它的蓝牙仅用于一次性初始化，这也是§4说明我们无法直接复用的根本原因。后者决定了本应用整体架构，而不只是传输层。

可以复用的是底层基础设施，这部分沉淀了大量工程经验：

| 直接复用代码 | 复用设计规则 | 不采用 |
| ---- | ---- | ---- |
| tauri-plugin-blec 调用逻辑；但不使用其自带btleplug补丁，不使用npm绑定。该补丁用于修复CoreBluetooth连接崩溃问题（deviceplug/btleplug#397），该问题在btleplug 0.13上游版本已修复，blec 0.14基于此版本构建；而他们的0.8版本早于该修复。并且他们维护的 crate与npm同步绑定机制不适用于Rust驱动客户端，因为webview不调用BLE | 不做过滤扫描，自行筛选目标设备；其扫描核心逻辑和本文§3.3独立得出相同结论，证明方案可行 | TanStack Query：它用于HTTP服务端状态缓存，本应用无HTTP服务端 |
| Android BLE运行时权限处理逻辑；这是选用blec而非裸用btleplug的理由 | 轮询探测设备，而非休眠后仅做一次快照（§3.4） | 初始化向导状态机（§4） |
| 全屏布局、`viewport-fit=cover`、安全边距、竖屏锁定 | 每个错误都记录可回退步骤，点击重试不会重置整个流程 | 字符串匹配式错误分类：configd以类型返回BadKey、NotFound；不存在的方法返回METHOD_NOT_FOUND |
| App Store上架合规与审核笔记，踩坑经验一次性沉淀 | 应用后台时BLE断开属于预期行为，不是故障：iOS会主动断开GATT链路 |  |
| x25519-hkdf-sha256-aesgcm 密码加密方案（前提：机器人文档§8.1最终采用上层加密而非链路层加密）；其报文格式已有文档，并有可用客户端可用于验证实现 | 连接失败可能表面显示成功，但订阅时卡死；需断开重连强制重新发现设备 |  |

## 3. 协议由Rust实现
tauri-plugin-blec同时暴露Rust与JS处理器，二者是同一个处理器：任意一端建立的连接，两端都可控制。因此应用依赖 `duck-ipc-proto` 定义有线协议类型，`duck-ble` 负责分片与GATT UUID管理；蓝牙链路由Rust驱动，向webview传递强类型命令。React不解析机器人返回报文，直接调用接口拿到例如NetStatus这类结构化对象。

这是最重要的复用能力，也是Reachy Mini无法实现的：**应用与守护进程协议不会发生版本漂移**。协议变更会直接导致应用编译失败，和btd路由表校验逻辑一致。历史上已经出现两次这类问题，提前捕获了字段不匹配问题，避免运行时从机器人收到异常数据。

这也是选用Tauri而非其他跨平台框架的核心理由（非常规理由）：所有跨平台框架都能提供一套代码；只有Tauri能让客户端直接复用服务端的原生类型定义。

`duck-ble` 正是为这个手机应用而抽离。GATT、帧封装、广播包原本属于btd，并且在源码中已经标记为有线契约。广播包文档明确说明：客户端单独编写的解码器很容易和服务端不一致，本项目在创建该crate前手写过一套解码器，验证了该风险。抽离独立包之后，手机端二进制不再为了一个模块打包clap、tracing-subscriber；同时 `duckctl` 编译Linux守护进程时，也不再引入bluer、定制libdbus，只依赖三份跨平台文件。

### 3.1 媒体流位置，以及该设计不存在安全漏洞
协议唯一不完全由Rust处理的地方是WebRTC数据通道。对等连接与`<video>`标签本身属于webview能力；不存在Rust方案可以直接把视频帧渲染到手机屏幕。但数据通道使用同一套JSON-RPC协议；如果在TypeScript手写报文封装，会再次引入本节要规避的协议漂移问题。

因此webview负责字节传输，Rust负责解析报文内容：每条请求都由`proto::Call`生成`proto::Request`构建，应用信令模块中完全不硬编码方法名。如果在ts文件直接写`{vx, vy, vyaw}`字面量，代码依然可以编译，但会出现错误的运动控制。

### 3.2 该设计消除的历史缺陷
Reachy Mini传输层实现逻辑：写入命令，同步读取响应特征值；如果应答是`OK:`确认，再等待通知事件获取真实负载。快速应答可能在读取操作前到达，负载留在积压队列，被下一条命令读取。该缺陷曾导致WiFi扫描返回空数据，拿到的却是上一条密钥交换的对象。修复方案是每次命令执行前清理过期积压报文。

本方案不会遇到这类问题。JSON-RPC依靠ID将请求与应答一一绑定；仅使用单个特征值，不存在写操作与通知事件的映射猜测；机器人文档§3.2规定机器人会销毁不属于当前对等端的会话。记录在此，避免移植传输层时顺带把这套临时修复方案照搬过来。

## 4. 蓝牙是永久通信通道，不是一次性配网步骤
这是最核心的架构差异，决定整个应用形态。

Reachy Mini的BLE代码只运行一次：向导流程到达终态后，切换局域网，蓝牙不再使用。Duck机器人的BLE在机器人整个生命周期内，都是交互主接口。

因此本应用不是“配网向导+附加设置页”。应用内置会话层，自动重连与重新认证。原因见§3.2：当中心设备断开，btd会销毁会话；手机重连后处于未认证状态。所有页面都需要支持底层链路断开后自动恢复，包括升级过程（应答发出5秒后btd会重启，见restart-order.md §1）；以及用户在浏览器完成设备码授权的场景，这也是`account.login`返回授权码而非token的原因。

机器人侧配套适配：`updaterd`记录每个组件最新进度，新订阅者接入时回放进度；升级过程中`update.status`从缓存快照返回数据。手机在升级中途断开重连后，会重新认证、重新订阅，并获取当前升级进度。

会话层是应用真正的核心，并且可测试。机器人文档§8.2提到：多机器人场景无法脱离硬件板测试；但链路断开场景可以。tauri-plugin-blec内置进程内模拟对象，可按需模拟断连、操作卡死。重连、重认证、重订阅都可以作为普通单元测试。已经发现3个真实缺陷：建立连接时订阅重复发送；重连时发现缓存清空，找不到目标机器人；从未建立成功的链路抛出下线事件。

## 5. 独立代码仓库
守护进程工作区统一版本，所有组件打包为单个制品发布。应用上架应用商店的发布周期不同，不属于同一版本主线，因此单独仓库。

microduck仓库开源，`duck-ipc-proto`、`duck-ble`以普通git依赖引入，无需密钥。依赖项刻意跟踪main分支，不锁定固定版本：协议变更导致应用编译失败，正是这套机制设计的告警信号。

## 6. 最低API版本门槛，与守护进程策略相反
握手阶段，应用拒绝连接API版本低于31的机器人（robot 0.14版本）。

该策略与守护进程完全不同。`app-path-design.md` §3明确：版本差异只上报，不拒绝连接。该策略适合守护进程：它是无网络场景下的传输通道，`net.connect`正是用来解决版本不兼容问题。

手机应用做了不同取舍，该取舍简化所有页面逻辑。一次握手校验最低版本后，页面可以直接认定字段存在、接口已路由、应答符合守护进程定义结构，不用各自猜测旧机器人可能返回的数据。在握手阶段发现版本不兼容，远好于操作到第四个页面才发现接口不存在。

代价明确：低于最低版本的机器人**无法通过手机APP升级**，因为APP拒绝通信。但`duckctl update apply`仍可以通过同一蓝牙链路连接，提示信息会说明这点。

**版本高于应用的机器人可以正常使用**。协议只新增字段；如果客户端拒绝识别未知字段，则机器人每一次升级，APP都必须同步更新。

## 7. 机器人侧尚需补齐的配套能力
全部由`app-path-design.md`负责定义；下面列表全部是面向应用侧的能力缺口：

- **加密（§5.5、§8.1）**：机器人交付前必须完成。应用需要下发WiFi密码，不能以明文在链路传输。该能力不阻塞应用开发；§8.1的三个候选方案中有两个不需要蓝牙绑定，因此应用基于未加密链路开发。
- **设备识别 identify（§8.2）**：让目标机器人做出动作，从列表多个同名设备中识别手上这台。已完成三分之二：`robot.do`已路由；§8.2中“没有驱动扬声器的通路”描述已过时，存在sounds crate，`robot.sound`是被禁止调用而非不存在。剩余需求：识别动作**认证前可用**。如果先要输入PIN码，而用户的目标就是把PIN发给正确机器人，会形成逻辑死循环。参考Reachy Mini的`PLAY_SOUND`：公开调用、无需PIN、扫描列表直接触发。
- **单机器人独立PIN码（§5.3、§8.2）**：没有生成、打印、记录PIN码的机制；PIN无法从设备身份推导，因为身份信息会在广播包对外广播。依赖硬件落地。
- **蓝牙绑定撤销（§5.6）**：“忘记此手机”是设置类应用标配功能，但暂无对应API。
- **恢复出厂设置（§8.2）**：没有接口清空configd配置；出厂预设名称和用户修改后的名称无法区分。
- **手柄在手机连接时重连（pad-minimal-pairing.md 故障3）**：当btd维持外设链路时，手柄控制器无法作为中心设备发起连接。会话期间打开已绑定手柄，手柄会保持闲置。守护进程层面无法修复，最直接的修复方案调用会失败。应用可按需让出链路20秒；临时解决办法为先打开手柄。

下面几项已通过应用验证，当初接口被禁止，实际使用后发现原限制理由不成立：
- **机器人直立（#301、#303）**：`robot.init`当初被拒绝，理由是“操作者应当看机器人，而不是看屏幕”，该逻辑同样用于`robot.do`、`policy.install`。`robot.enable`被误判为遥操作（实际不是：单次请求，非每秒50次高频指令）。缺少这两个接口，APP只能查看机器人信息，无法控制动作；最终通过游戏手柄场景推动开放。
- **通知报文上限512字节（§3.6、#292）**：由本应用发现，duckctl可复现。btd按MTU-3计算应答长度；CoreBluetooth MTU=517，超出特征值最大承载限制2字节。中心端静默保留前512字节，丢弃剩余内容。`{"security":…}`会被截断成`{"serity":…}`；如果截断位置恰好是换行，则请求直接无应答。
- **区分多台机器人（§8.2）**：设备名称来源于SoC序列号，广播包携带IPv4。首页列出名称与地址，无需预先连接。APP以序列号作为主键，蓝牙地址仅作为缓存，完全遵循§8.2规则：如果另一块板子复用旧的缓存地址，会按设备名称拒绝，而不是静默认错设备。

## 8. 待解决事项
- **PIN码页面**：出厂PIN固定为000000并在代码库公开。当前PIN页面要求输入的密钥没有保护作用，在最需要流畅的流程里增加交互卡点。应用目前静默发送PIN。当硬件支持打印每台机器人独立PIN码后，再启用PIN输入页面，同时展示“PIN错误，剩余2次尝试”提示。
- **手机端游戏手柄配对**：`pad.pair`、`pad.forget`、`pad.bind`以及技能表编辑接口已经路由，但尚未接入。`route.rs`说明`pad.bind`设计基于BLE：手持机器人的人同时拿着手柄。上面故障3说明，手机端配对手柄的难度高于路由定义预期。
- **是否单APP支持两款机器人**：暂不支持。会在正式版本引入第二套协议方言，两个场景仅共享传输层。未来如果定为目标，前提是协议统一，而非UI统一。
- **UI组件库**：暂未引入。应用CSS仅约300行。MUI是首选候选，但目前没有使用需求。后续如果页面需要单纯CSS无法实现的组件，再评估，无需提前引入。
