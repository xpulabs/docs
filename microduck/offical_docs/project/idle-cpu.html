Microduck

无人交互时机器人的运行行为

一台放置在桌面上、未连接手柄、无查看器接入、没有任何驱动指令的Duck机器人，依然会运行5个守护进程。本文描述该状态下各进程原本的工作方式、已做的优化变更；对于两个未改动模块，也给出保留现状的量化依据。

文中所有数据，要么基于代码做数值推算，要么在开发主机上实测。只有测试图案相关指标在硬件板卡上完成实测；最后一节说明其余指标还需要哪些板上验证。

资源开销项（优化前后对比）

模块优化前空闲开销优化后空闲开销
mediad 原始分支每秒拷贝1.84MB，30次/秒有读取方请求时才拷贝，约2次/秒
mediad 测试图案CPU渲染720p30画面，占用单核29.4%256×144@5fps，像素处理负载仅原0.7%
tofd 帧轮询约100次I²C读取/秒约45次/秒
padd（已接手柄、摇杆居中）50–100条消息/秒10条消息/秒
抚摸检测（启用时）约400次FFT/秒 + 4次前向推理/秒环境有声响时才执行，静默时不运行

mediad：每一帧都执行拷贝

appsink回调会把tee分流出来的每一个缓冲区复制到缓存槽，读取方从中获取最新帧。 720p30是正式发布画质，media.source默认使用摄像头。一帧UYVY图像大小：1280 × 720 × 2 = 1.84 MB。 读取方为自动曝光（2Hz）与Duck检测（启用时2Hz）。30次拷贝里有28次完全没有使用者：开机后持续产生55MB/s内存拷贝，每秒30次分配1.8MB内存。

优化逻辑：改为由读取方主动发起请求，回调在下一帧就绪时返回数据。 如果直接返回上一帧会更省资源，但会把读取方自身轮询周期引入测量；曝光控制回路会基于半秒前的亮度值进行调节，无法稳定收敛。

测试图案原本按摄像头分辨率渲染

当板卡配置 [media] source = "test"，会使用videotestsrc视频测试源。这样不带摄像头的机器人仍可维持完整会话：信令、协商、数据通道、控制API全部复用视频流。测试图案原本使用[media]画质档位，和摄像头输出分辨率一致。

两者的核心差异在于像素来源： 摄像头帧由硬件ISP输出，v4l2src转发几乎无开销；测试图案则由软件进程逐帧绘制UYVY打包图像。 两块同型号板卡，无外设接入、处于空闲状态：

数据源mediad空闲CPU占用
摄像头，rkisp6.1%
测试源，720p3029.4%

测试图案的CPU开销是摄像头方案的5倍。即便所有读取方都未订阅，依然每秒合成30帧、每帧1.84MB图像。该板卡的camera.json显示："frames":23142，"consumers":0（消费者数量为0）。

优化后：测试图案使用TEST_PATTERN_GEOMETRY：256×144，5fps，16:9，和所有画质档位一样按8字节对齐，单帧73KB。像素处理负载仅原来的0.7%。 这不是画质妥协：测试图案本身不需要高分辨率。media.video上报该小尺寸分辨率，因为这就是机器人实际输出的画面。

tofd：15Hz传感器原本每秒轮询100次

帧间隔66ms，程序每10ms执行一次data_ready查询。获取1帧数据大约需要7次I²C通信，其中6次查询无新帧。 优化后，循环会跳过传感器不可能产出新帧的时间段，仅在其余时间轮询。帧的时效不变：依然受10ms轮询粒度限制，两种方案检测到帧的时间精度一致。

只要搭载ToF传感器，无论是否启用特雷门琴功能，该进程都会运行：tofd持续测距并推送数据给订阅者，无订阅者是常态，轮询逻辑不依赖订阅者。 [theremin] enabled默认关闭，且该开关不影响此项开销；它节省的是robotd的挂起读取操作，并非本次优化对应的开销。

padd：每秒重复发送三组零值共50次

摇杆采用轮询读取，手柄静置时每周期输出完全相同的帧：编码、写入、刷新，robotd侧还要解析。在同时发送归零robot.move的两种模式下，开销翻倍。 优化后，内容完全相同的帧会暂缓发送，两类指令复用一次写入。

仅当指令要求无运动时，才暂缓发送帧。该设计规避[safety] deadman_ms（安全看门狗超时，padd无法读取该参数）：看门狗仅将扭转量置零，不修改其他数据。如果帧本身就是零运动指令，暂缓发送不会产生影响；如果是运动指令，该机制会在摇杆保持按下时停止机器人。

抚摸分类器：静默环境下仍持续推理

1秒窗口内包含40个log-mel梅尔频带，每秒执行4次推理，每次包含100次512点FFT + 一次神经网络前向传播。 配套的环境收音模块一直在监测环境底噪，因此分类器改为仅在声音明显高于底噪时才运行；抚摸场景除外，抚摸结束的边界需要和起始边界一样，依靠推理识别。

该功能默认关闭，属于可选开销，不是所有机器人常驻的负载。

保留不变的模块及原因

50Hz总线写操作，不做条件化执行

safety.apply每个周期写入16个目标位置，包括机器人停泊、目标位置无变化的周期。如果改为条件写入，收益如下：

总线层面：Protocol 2.0同步写16个舵机，报文94字节（4字节头部 + 1广播ID + 2长度 + 1指令 +4地址/长度 +16×5字节负载 +2 CRC）。1M波特率下耗时940µs。 同周期同步读取17个设备约422字节，耗时4.2ms。20ms周期内总线负载约25%，本次写操作占总线时间的1/5，不是性能瓶颈。

CPU层面：一次write(2)写入94字节，包含底层tty层，连同中断处理约15µs；50Hz频率下仅占用单核0.075%。

权衡：这条写指令是循环中保证舵机收到目标位置的关键语句。如果增加条件判断，就需要枚举所有会让舵机目标位置失效的场景：扭矩开关、电压跌落、舵机清除锁存故障后自重启、init插值指令等。一旦逻辑遗漏，会出现机器人在未知场景下无法维持姿态的故障。仅仅节省0.075%单核资源，不足以承担该风险。

robotd空闲周期其余部分已经高度精简：ONNX推理仅在驱动机器人时启用；状态帧仅在存在订阅者时组装；电压、温度寄存器每秒读取一次，而非每个周期；串口读取采用休眠等待而非忙轮询。

多线程Tokio运行时：保持现状无需改动

robotd、configd、updaterd直接使用#[tokio::main]，RK3566平台每个进程默认按核心数启动4个工作线程。空闲工作线程会挂起，不会持续轮询。 测试：4个工作线程、4个挂起任务的多线程运行时，对比单线程current_thread运行时：

multi:   5线程  初始CPU 0.01s → 20s后 0.01s
current: 1线程  初始CPU 0.00s → 20s后 0.00s

差异仅来自4个挂起线程的栈内存，不产生发热。切换运行时类型无法降低本文讨论的CPU开销，还会引入真实风险：current_thread模式下，异步链路中的同步调用会阻塞整个运行时（包含IPC套接字）。updaterd多处存在这类调用：engine.rs读取签名、写入嵌入式清单、遍历单元目录；只有重型校验任务放到spawn_blocking。

仍需要硬件板卡验证的项目

以上所有数值，要么基于帧大小、报文结构、轮询间隔做理论估算，要么在开发机上测得。四项优化都需要在真实硬件上验证发热情况：

  1. mediad、tofd、padd优化前后CPU占用，使用dev-push.sh和top -H采集。摄像头相关指标变化应该最明显。目前仅获取0.12.0版本mediad空闲数据：摄像头6.1%，720p测试图案29.4%。这是优化后数据，缺少优化前基线；tofd、padd暂无任何板上实测数据。
  2. 在那块测得720p30占用29.4%的板卡上，实测256×144@5fps测试图案。理论计算像素负载为原0.7%；实际剩余开销来自videotestsrc每帧固定开销，该开销不再随图像分辨率线性增长。
  3. 10分钟空闲状态SoC温度，这是本次优化的核心指标。之前视频翻转问题导致板卡温度达到97℃，降频至408MHz。空闲时的温度余量，决定机器人一边识别画面一边行走的稳定性。robotctl health现在可以同时打印温度与降频阈值，查看降频状态不再需要SSH登录（参考 ../design/robotd-design.md §2.1）。
  4. tofd针对传感器时钟偏差的保护逻辑。轮询以帧到达事件为基准，允许传感器提前20ms（周期误差30%），但尚未在VL53L8传感器上实测该场景。
  5. 在普通室内环境验证：抚摸检测触发速度和之前保持一致（而非静音环境）。

后续发现

头部传感器是遗留问题。在板卡执行ps -L查看线程后定位：tofd空闲约5%CPU中，4.5%来自头部IMU，0.5%来自深度传感器；而IMU在整个系统中没有任何数据消费方。 也就是说，本文优化的轮询逻辑并不是真正的开销来源；真正应该关闭的是这个无人使用的传感器。详见 tof-on-demand.md。
