安装流程缺少测试

状态：已关闭 · 日期：2026-08-05，修订：2026-08-07、2026-08-11 · 负责人：pierre

连续四个漏洞都流转到硬件板卡上，全部发生在安装流程，418项测试和board-test.sh均未能捕获。本文记录问题成因以及修复方案。本次事件提炼出一条通用准则：全新安装对板卡执行的任何操作，都应放到钩子脚本中。因为钩子脚本是唯一会在每块板卡、每次更新时执行的代码。该通用准则内容较多，现已独立写入 updater-design.md §9.1，请查阅该文档；本文侧重事件复盘，并非规范文档。后续该准则又被两次误用，因此新增安装步骤前，建议先阅读§9.1，而不是事后再看。本文在问题刚发生、细节清晰时撰写，保留原文过去时态，不作参考文档式改写；现在它的价值在于展示错误的形态，而不是代码仓库当前状态。

第二部分介绍两个容易混淆但本质不同的现象：正在运行的守护进程与刚安装完成的新版本之间出现版本不一致。无论增加多少安装测试，都无法捕获这两类问题，需要单独修复。这部分内容保留在此而不是单独建文档，是因为排查其中任意一个问题时，工程师很容易误以为是另外一个。

修订说明。四个漏洞均已修复，后文版本不一致问题也全部解决：场景1落地了serde(default)规范；场景2的握手校验方案被否决，否决理由已归档；“服务单元生命周期长于安装它的版本包”这个副作用，从隐性行为改为主动拦截。

标题所说的测试缺口现已补齐。新增测试可以安装真实制品包：board-test.sh解压制品包，运行install.sh以及hooks/postinstall；校验每个systemd单元ExecStart指向的二进制是否存在于对应的压缩包；每次执行dev-push.sh都会执行板卡校验；scripts/systemd-test.sh基于真实systemd执行完整更新。下面是整套方案，以及各测试发现的问题；最后一项测试还找出了两个引擎漏洞。

初稿完成后有一处重大变更，需要在此说明：updaterd与btd现在会在更新应答返回数秒后重启（RESTART_AFTER_REPLYING）；新版本自带的updaterd会在提交前完成自启动校验（updaterd --self-test）。原文中有两处描述基于旧逻辑，现已失效，均已就地修正；第二小节的前提尤其不再成立。

第二次修订说明。§4中版本不一致相关问题已通过代码彻底解决，不再只靠文档说明。所有守护进程都会上报自身运行版本（duck_ipc_proto::publish_identity）；updaterd每次启动时，对比每个单元与当前生效版本，对过时进程执行重启（updater/src/reconcile.rs，Engine::reconcile_running_units）。原文另外两处描述当时成立，现在不再适用：一是“运行版本与安装版本不匹配时无处理逻辑”；二是“无法读取btd正在运行的版本”，两处均就地修正。docs/design/restart-order.md §5、§7描述这套机制以及版本不一致的排查方法；本文保留当初为什么需要这套机制的背景。

漏洞情况

四个漏洞在一天内全部暴露，均发生在向开发板安装btd和configd的流程。（最初记录为3个，§4补充后变为4个）

  1. on_apply用一条命令批量重启多个单元。systemctl restart robotd configd只要其中任意一个单元未知，整条命令直接失败，已存在的单元也不会重启。 引入新守护进程的版本包因此无法完成任何重启操作：单元文件随新版本包才落地，没有任何脚本提前安装它。回滚提示：30秒内健康检查失败：无法连通，报错信息不指明具体单元，也不说明执行的命令。 属于潜在漏洞而非致命故障，因为板卡会保留本地/etc/robot/updater.toml。

修复分两轮，第二轮才是真正修复。第一轮防御性修复：逐个重启单元，遇到systemd未知的单元直接跳过。第二轮根治：hooks/postinstall负责安装版本包内的单元文件。更新引擎一直预留了安装后钩子执行点：解压 → [pre_install] → 版本切换 → [post_install] → apply → 健康校验。钩子在版本软链接切换之后执行，因此ExecStart路径可以正常解析；又在重启动作之前执行，on_apply执行时单元文件已经存在。但该钩子一直没有被使用；只有scripts/install.sh会从版本包拷贝单元文件，因此每新增一个服务，都需要在每块板卡上手动操作。评审阶段有人指出该机制存在但未启用，并非我发现。

  1. 制品包缺少新增的单元文件。打包流程用显式--include声明所有要打包的文件；单元文件加到install.sh，却没有加到打包包含列表。排查方式：在板卡执行ls current/systemd/手动发现。

  2. 制品包缺少新增二进制文件。打包阶段通过cp逐个复制二进制；cargo board --bins编译出btd和configd，但没有将文件放入待打包目录。btd.service报203/EXEC，该错误容易被误判为守护进程本身损坏，而不是制品包缺失文件。

漏洞3与漏洞2属于同类问题，在同一个文件内。在增加用于防止漏洞2复现的测试之后，隔两个提交引入漏洞3。该测试只校验单元文件，不校验单元执行的二进制。两次修复本身都正确，但修复范围都过于狭窄。相比单个漏洞，这种“修复片面”的模式才是需要重点解决的问题。

  1. on_apply的重启列表保存在板卡本地配置，新增守护进程永远不会被重启。（已实测，代价最高，之前归类为潜在非致命漏洞） [component.daemon.on_apply].units从/etc/robot/updater.toml读取，这是运维配置文件，install.sh会刻意保留，不覆盖。引入configd的分支虽然把它写入发布版deploy/updater.toml，但在该分支之前初始化的板卡，配置会永久保留units = ["robotd"]。所以每一次configd版本更新，二进制文件虽然替换，但旧进程继续运行。

故障现象导致定位耗时两小时，而不是两分钟：

  • 更新上报成功：版本切换完成，健康校验通过，无报错；
  • 执行robotctl update apply返回already_current，不执行任何操作，最直观的恢复命令完全无效；
  • 守护进程仍正常响应，但运行旧代码，让人误以为修复代码本身有问题，而不是没有重启；曾有四项WiFi相关修复，验证时发现失效，根源就是进程根本没有切换到新版二进制。
  • robotctl version其实可以诊断该问题，提示文字：configd运行版本X，但安装版本为Y……要么重启未执行，要么重启失败。只是没人主动运行这条命令。一个存在但没人去执行的诊断工具，价值等同于不存在。这也说明最好让更新流程自身检测异常，而不是依赖更多诊断命令。

修复（engine.rs::units_to_restart）：重启单元集合从版本包自带的systemd/*.service文件推导，再合并配置文件里声明的单元，排除updaterd和btd。这两个进程从“由测试约束的配置约定”改为代码内NEVER_RESTART常量：这是守护进程本身的特性，不是运维人员可选配置。即使板卡updater.toml是在该守护进程新增之前创建的，现在依然会自动重启该进程，无需人工修改配置。下面保留推导逻辑，用于论证这类列表应该放在哪里。

重启单元集合应从版本包读取，而不是板卡本地配置。版本包自带systemd/*.service，本身就声明了它提供哪些单元。这和选用hooks/postinstall来安装单元是同一个思路。更新引擎可以重启版本包自带的单元，排除两个文档约定的例外：updaterd（正在执行本次更新）、btd（更新请求的传输链路）。这样新增守护进程的版本包会在所有板卡上自动重启该进程，无需运维修改配置，也不会出现板卡配置静默过期。

文档记录了两个备选方案，作为补充而非替代方案：

  1. apply增加--force参数，对已经是最新版本的包，重新执行钩子脚本与重启。已有先例，install --force就是用来解决同类鸡生蛋问题。
  2. already_current逻辑不只对比安装版本，还对比正在运行的版本；只有发现版本不一致时，不再直接返回无操作。

第二个备选方案的最终实现不在提案处。它本质要解决：运行版本与安装版本不一致，是直接报错拒绝，还是自动修复。最终方案选择自动修复，由updater/src/reconcile.rs实现，在每次updaterd启动时执行，而不是放在apply流程内。每个单元的运行版本读取自进程发布的身份文件，与组件当前生效版本对比，过时单元自动重启。updaterd每次更新应用完成5秒后会自重启，因此该校验在每次apply之后数秒就会执行。Engine::apply主体逻辑不用改动，就能自动修复这类版本不一致。

剩下一个边界场景，现已修复。reconcile刻意不修复updaterd自身版本不一致：负责故障恢复的进程如果自重启，会形成死循环，没有退出路径。于是出现唯一场景：updaterd版本过时，运维执行apply，返回AlreadyCurrent，不调度重启，只能手动执行systemctl restart updaterd修复。

修复（engine.rs::restarts_owed、reconcile::stale_units）：apply与select在判断already-current分支时读取同样的身份文件，在already_current结果中标注运行版本不一致的单元，并像普通更新一样调度延迟重启。不会触发启动校验要防范的死循环：该重启只在收到请求时执行一次，并且通过systemd-run拉起，不是在待重启进程内部执行。

apply --force方案被放弃，不是延后实现。它的目的是对已是最新版本的包重新执行重启；现在apply本身就会在确实存在版本过期时执行该操作。增加flag会提供第二种触发方式，同时还要处理复杂判断逻辑：install --force在robotd正常工作时拒绝执行，因为它会关闭健康校验；apply保留健康校验，如果照搬这个逻辑，当机器人正常运行但版本不一致时，该flag会失效。现在不再需要这个参数。

本段已修正（原文描述错误）：btd在更新过程中不参与即时重启，因为重启会断开承载更新进度的BLE连接，这一点至今仍然成立。但原文推论错误：曾认为btd修复需要手动重启或整机重启，手机端流程存在缺口。现在不再是这样。更新结果上报完成后，该排除限制失效，btd和updaterd都会在5秒后通过systemd-run --on-active=5s重启（RESTART_AFTER_REPLYING）。客户端收到更新结果之后连接断开，BLE场景下属于正常重连。

本段同样已修正（原文描述错误）：之前认为可观测性存在短板：robotctl version无法读取btd版本，因为btd不对外提供socket接口，没有查询入口。该假设前提是版本信息必须通过socket查询。现已改变：所有守护进程启动时都会将身份信息写入文件，包括btd、padd。robotctl health读取每个进程启动对应的版本包，当和安装版本不一致时给出告警。不再因为上面这个原因出现无法观测的守护进程。

一个值得关注的副作用：服务单元生命周期长于安装它的版本包

hooks/postinstall安装版本包自带的单元文件；设计上，版本回滚时不会删除这些单元文件。替代方案是记录新增的单元，回滚时删除，但钩子注释说明该方案收益不大：下一次成功更新会重新部署对应单元。

这套逻辑在单纯回滚场景没问题。但如果降级到一个该守护进程还不存在的旧版本，就会出现问题：单元文件保留，它的ExecStart指向旧版本包不存在的二进制，守护进程报203/EXEC。一旦该守护进程被加入on_apply重启列表，重启失败会直接导致更新失败并触发回滚。

现场复现案例：板卡运行开发版本，执行robotctl update apply daemon，切换到稳定版0.2.0（该版本还没有configd）；configd.service启动失败；更新引擎执行回滚并上报。行为本身合理：板卡不应该静默降级到低于该守护进程引入版本的固件。但没有明确规则描述该约束，报错只提示systemd启动失败，看不出根本原因。

现在增加显式校验，不再是隐性行为。updater/src/orphan.rs会拒绝候选版本包：如果某个已安装单元的ExecStart二进制在候选版本里缺失，直接拒绝更新。拒绝提示会写明单元名称、缺失二进制以及解决办法：删除单元，执行systemctl disable --now configd.service && rm /etc/systemd/system/configd.service。没有强制覆盖参数：删除单元本身就是运维的真实意图，因为版本低于守护进程引入版本的板卡，本就不该运行该守护进程；下一次携带该单元的版本更新会重新安装。

执行时机两点说明：

  • 不在前置预检（preflight）：预检阶段无法读取候选包文件列表，两次预检都在制品包下载之前执行。校验放在解压之后、版本切换之前，此时临时目录还可以丢弃，不会改动系统。
  • 所有目标都生效，不像Error::WouldDowngrade仅针对Latest源：后者用来防止镜像提供过时清单；本校验用于防止单元无法启动，在Ref指定版本场景下也会触发，也就是本次观测到的场景。

不会在回滚、恢复出厂、版本切换（select）时执行。这些操作是主动回退版本，是板卡从坏版本恢复的手段。因此带拒绝逻辑的校验不能放在恢复链路（docs/design/architecture.md §1.1）。回滚后遗留孤立单元，维持文档描述行为，并且可以自我修复。

原有测试为什么没能捕获漏洞

不是指责测试；原有测试只覆盖它声明的范围。问题在于存在完全没有覆盖的场景。

本文最初撰写时，结论是“完全没有覆盖”，相关记录已经变更。保留下表记录历史缺失项，同时标注当前各测试覆盖范围：

测试覆盖范围不覆盖
board-test.sh在aarch64真实Linux下执行二进制；解压真实制品包，通过stub版systemctl运行install.sh与postinstall钩子；校验文件放置、权限、执行顺序、幂等性，以及每个单元ExecStart对应的二进制存在服务是否真正启动（需要真实systemd）
xtask tests校验工作流YAML与install.sh一致性，单元ExecStart和待打包二进制编译产出的制品包是否和源码描述一致；只读取源码文件
updater tests引擎、日志、校验、回滚，全部使用模拟对象完全不测试install.sh
shipped_config_is_safe_for_a_client_robotdeploy/updater.toml配置内容配置是否可正常安装

第一行原文描述曾经是“解压制品包、安装单元、启动服务”，配套说明：没有任何测试会安装真实制品包。这正是本文要解决的核心痛点，现已修复。xtask测试仍然属于较弱校验，只校验两份源码定义一致，而不是观察最终打包产物，但它不再是打包错误和板卡之间唯一的防线。

测试补齐方案

修订于2026-08-11，在下面重启机制落地后新增一条当初未写明的约束：CI已经是迭代流程里最慢环节，评估方案时不仅看覆盖能力，还要评估新增等待耗时。下文会写明每个测试的运行位置。

资源预算（CI耗时）

每次代码提交、PR都会并行执行CI任务，CI是否通过取决于最慢任务耗时，不是总耗时。这一点决定新增测试放在哪里：

任务耗时来源
check格式化、clippy、cargo test --workspace、安装脚本lint、xtask打包
board源码编译cargo-zigbuild + QEMU aarch64仿真
coverage完整插桩编译

毫秒级的测试加到cargo test几乎无感知；任何放到board或coverage任务的测试，每次提交都会增加耗时。由此引出三条核心规则：

  1. 默认cargo test --workspace只运行进程内单元测试；不处理压缩包、不调用systemd、无网络、无sleep。
  2. 解压制品包、启停服务类测试按需手动执行，写成脚本或#[ignore]测试，不加入PR门禁。
  3. 不新增CI任务。如果校验需要制品包，挂载到xtask打包步骤，复用该步骤已经构建的tar包。

两项优化削减了CI耗时，比新增测试收益更大：

  1. coverage任务原本在PR中对基线和HEAD两次完整插桩测试，只为输出覆盖率差值。已移除，改用--fail-under-lines捕获回归。任务耗时从7分钟以上缩短至约2分钟。覆盖率阈值现在是单向递增，低于阈值才拦截；改动降低覆盖率但仍高于阈值时，不再告警。
  2. 纯文档变更会触发全量跨平台编译与插桩构建。原因：on触发器没有路径过滤，修改本文档就会触发QEMU aarch64编译+全量插桩构建。本文撰写期间连续三个文档PR都触发了该流程。现已增加paths-ignore过滤docs/**和*.md。

该优化有坑，已经核验：被过滤的任务不会上报任何状态。如果该任务是合并必需门禁，文档PR会永久pending。本项目main分支没有强制门禁，所以安全；分支保护API访问返回403。后续开启分支保护时，需要重新评估，方案改为过滤任务 + 同名空任务占位。

1. 无需新增基础设施的两项单元测试

进程内测试，归入cargo test，覆盖自动修复更新机制的核心逻辑，这两块之前无法被任何测试观测。两个测试均已编写，下面是设计思路。

  • systemd-run调用行为不可观测：schedule_deferred_restarts硬编码Command::new("systemd-run")；相隔两个函数的SYSTEMCTL定义为常量，方便重启测试替换桩脚本。同样改造，增加断言：校验--on-active=5s参数、每个单元单独调用、包含updaterd与btd。该参数即使写错，旧测试也全部通过。
  • reconcile::check没有测试调用，只测试纯判断函数verdict_for。它支持传入systemctl句柄，身份文件读取走DUCK_RUNTIME_DIR，注释明确预留该接口用于测试。在临时运行目录写入身份文件，断言4种结果：过期单元被重启；updaterd上报但不重启；缺失身份文件不处理；重启失败上报错误。

2. 制品包安装测试：已完成，遗留缺口

该问题已经解决，标题对应的缺陷不复存在。scripts/board-test.sh基于_build-release.yml的--include列表打包正式版本，在容器内解压，使用桩systemctl运行scripts/install.sh和hooks/postinstall（PR #47，2026-08-07）。共11项断言：单元文件字节一致、权限644；sysusers配置片段；robotctl软链接指向current；journald配置片段；daemon-reload在enable之前执行，configd早于btd；运维配置文件保留；二次执行幂等；install.sh不识别的单元，安装后不自动启动；postinstall脚本可以独立完成全部安装。

覆盖本节原来目标，同时包含“校验制品包内容”，因为tar包此时已经解压。漏洞2通过制品包校验而非YAML校验解决。

仍然留有一处缺口，对应漏洞3，是四类漏洞里最弱的测试项：没有校验单元ExecStart指向的二进制是否在本次打包的制品包中。这正是btd.service报203/EXEC的根源：制品包看起来完整，但缺少二进制。原有防护是xtask/tests/artifact.rs，对比工作流和install.sh，也就是前文批评的“仅两份源码比对”模式。现在增加三行代码，在已经解压源码、current软链接就绪的任务里直接校验。

仅校验版本包内部的ExecStart路径。单元可以刻意执行基础分区内的二进制：引导恢复网络就是如此，防止损坏的版本包破坏恢复环境。强制要求这类二进制打包进版本包属于过度严格，是错误的。

至此，该模块没有实质性缺失项。剩下下面两项，覆盖别的维度，不是重复校验。

3. 板卡校验：已完成，嵌入dev-push.sh

独立脚本不再单独实现。dev-push.sh原来只判断“更新已上线”，也就是版本切换、健康校验通过，但不校验五个守护进程是否运行新版二进制。这个缺口会造成长时间排障：曾有四项WiFi修复，验证失效，原因就是configd根本没有重启。

因此校验在每次push时执行，不是发布前才执行。读取每个守护进程启动时发布的身份文件，对比里面标注版本与板卡current版本；同时单独对比本次push构建版本（否则如果全部进程刚好是上一个版本，会误判通过）。robotd、configd、padd要求立刻匹配；updaterd和btd最多轮询等待30秒，因为它们会在应答5秒后重启。

这是唯一端到端验证整套重启机制的测试，CI无法替代：临时定时器、存放身份文件的RuntimeDirectory=、5秒延时都依赖真实systemd时序。单元版本过期会直接让push失败并给出定位信息。

两处设计为不阻断提交：

  1. 守护进程未上报身份文件，仅告警不失败：单元停止时systemd会删除运行目录；手动禁用padd也会出现该现象。
  2. robotctl health只做状态上报：不带舵机供电的工作台板卡会上报降级，这是工作台硬件状态，不是构建产物问题，和健康校验逻辑保持一致。

4. 真实systemd测试：已完成，scripts/systemd-test.sh

已落地，在断言之前就发现了代码缺陷。scripts/systemd-test.sh启动systemd作为PID1，生成三份带真实单元和updaterd的签名版本包；安装第一个版本，通过运行中的守护进程升级第二个版本，再安装一个自带无法启动单元的版本。

可以观测到其他模拟测试无法覆盖的四点（其他测试都用stub systemctl）：

  1. on_apply确实重启版本包自带单元；校验单元主PID变更，而不是仅校验命令被调用。
  2. 延迟临时定时器正常触发，替换updaterd，约4秒完成，新进程运行新版本。子进程无法实现该逻辑：子进程会留在cgroup中被杀死，这就是选用systemd-run的原因，之前该逻辑一直没有实测。
  3. hooks/postinstall能够安装、启用、启动板卡从未部署过的单元。
  4. 单元安装成功但启动失败，更新失败并指明单元：restart failed: Job for broken.service failed，而不是笼统回滚提示30秒内健康检查失败：无法连通。这对应漏洞1，是上面几项测试无法覆盖的场景。

使用Docker，而非systemd-nspawn，和本节最初提案不同。CI环境不推荐特权容器，但该脚本不在CI执行。选型理由遵循本节自身的优先级：只能在少数开发机运行的测试，容易被遗忘。Docker Desktop可以在开发笔记本上运行带systemd(PID1)的特权容器；nspawn做不到。

首次运行就发现代码bug，不是脚本本身问题：self_test_updaterd执行新版二进制时不带--config参数，它会沿用当前运行守护进程读取的/etc/robot/updater.toml做校验，失去原本目标：捕获新版二进制拒绝板卡配置文件的问题。

脚本内包含两组注入场景，生成其他测试无法断言的结果：

  1. systemd-run调用失败：更新仍然成功（设计上调度是尽力而为，更新已经提交），日志记录该失败；btd、updaterd停留在旧版本，就像定时器丢失一样。下一次updaterd启动时，reconcile.rs自动修复过期btd，并且不重启自身，避免死循环。这是reconcile.rs第一次在单元测试外闭环验证。
  2. 版本包自带User=用户的单元：postinstall安装sysusers.d文件，在启动单元前执行systemd-sysusers，注释说明该顺序是强依赖。用户创建成功，单元正常运行。反面场景：同样单元，没有前置创建用户，更新失败并提示单元，而不是报账户不存在。

测试框架执行途中发现并修复的缺陷

某次更新失败，提示回滚失败，但机器人已经成功恢复到旧版本。使用上面缺失用户的版本包复现。设计文档将RollbackFailed定义为最高严重等级故障，值得详细记录。

根因不是回滚流程本身。hooks/postinstall覆盖单元文件，设计上不会还原：注释说明，如果新版本安装失败，单元文件会保留，直到下一次版本包覆盖。该逻辑不变。没有预料到：回退目标版本的重启列表包含该单元。回滚会再次执行重启，继承同样的启动失败。普通坏版本就会触发，不限于降级场景：连续两个版本使用相同单元名，新版本单元损坏。

修复方案：版本切换(swap)和apply动作解耦。只有版本切换才属于恢复操作。完成swap_to并清除试标记后，机器人已经切回旧版本；后续单元重启失败属于第二件独立事件，不代表版本回滚失败。 Error::RollbackFailed含义保留：完全无法将机器人恢复旧版本。回滚过程中apply动作失败，保留错误信息并打error日志：

not healthy within 30s: …; the release was reverted, but restarting robotd failed: …

Restart=可能后续自动拉起；robotctl health可以查看最终状态。 按用户需要顺序展示两条信息：先说明更新失败原因，再说明回滚后单元无法拉起。

本段原文描述有误，多次误报，现已修正：所有守护进程配置Restart=always。进程立刻退出会快速耗尽systemd的10秒内最多5次启动限制，在健康检查30秒超时之前，重启请求被拒绝Start request repeated too quickly，稍后单元自动恢复。工作台板卡曾在robot healthy的日志行下方直接打印故障告警。restart_one现在使用reset-failed清空计数器，重试一次，消除该问题；上报观测到的拒绝错误，并给出排查命令。

两个被否决的备选方案（都有一定合理性）：

  1. 让postinstall支持回滚撤销：该钩子明确拒绝这个方案。需要在版本包外维护状态，在恢复链路引入新故障点，恢复链路必须尽量简单稳定。
  2. 全局容忍重启失败：会弱化restart_one的设计意图——存在但无法启动的单元，正是用来捕获坏版本的机制，在安装阶段仍然视为致命错误。

不采用的方案

把板卡作为自托管CI runner：运维成本高，CI单点故障。第3项方案按需执行，已经覆盖大部分收益，机器人实体适合放在房间内按需测试。

第二个独立问题：开发通道的版本不一致

在同一轮测试中发现，极易和上面安装漏洞混淆。无论多少安装测试都无法捕获，两种场景制品包本身都是完整正确的。

最初描述的前提已经失效：原文写updaterd在更新期间不会自重启(§4.1)，一直运行旧二进制直到重启整机，机器其他组件立刻切换新版本。这是下面两个案例的根因，现已修复。updaterd现在在更新应答返回5秒后自重启。版本不一致窗口仅数秒，不再需要等到整机重启。

基于这个背景看下面两个案例，都不再是线上事故，均已关闭：场景1落地serde(default)修复；场景2否决握手校验方案并归档理由。

  • 场景1的serde(default)修复不会因为窗口变短而失效：版本不一致只是触发该问题最常见场景，任何新版解析器+旧版发送者组合都会触发。在“默认值为合理零值”的字段都做了该处理。
  • 场景2握手校验的修复价值大幅降低：从“恢复命令直接失效”变成“存在5秒失效窗口”。论证后发现原有假设不成立。保留精确不等判断，修改提示信息，参见#77。

两个真实案例，每个排查耗时约一小时。

场景1：HealthResult新增必填字段

main分支在IMU模块增加consecutive_stale_blocks，发布0.2.0。在该改动前合并main的分支，不会发送这个字段。robotd运行完全正常：socket服务、加载两套策略、50Hz循环。但是正在运行的0.2.0版本updaterd收到应答，因为缺少字段直接拒绝。RobotIo::health把解析失败映射为Health::Unreachable，健康网关报30秒健康检查失败：无法连通。机器人本身完全正常，却回滚了正常版本包。

两项小修复，均已落地：

  1. HealthResult新增字段加#[serde(default)]，新版updaterd可以解析旧版robotd报文。所有在该字段新增之前的分支，使用--ref安装都会触发这个问题，覆盖整个开发工作流。 坑点在嵌套结构体：顶层字段（包括imu）已经加#[serde(default)]，但是嵌套ImuHealth内的consecutive_stale_blocks没有。现在ImuHealth、BusHealth在容器层面加上该注解，新增字段自动填充默认值，不会整体解析失败。

LoopHealth、Battery、MotorThermal刻意不加。这正是修复的关键：这些是测量值，默认填0属于虚假数据，旧发送方根本没有上报该值。例如电量百分比默认0，会把满电电池识别为空。规则是：只有字段缺失时零值符合真实语义，才加默认，不是所有字段都加。ImuHealth文档注释逐条说明。

  1. 新增独立状态Health::Incompatible，不再复用Unreachable。报错提示：应答结构无法被当前updaterd识别，而不是暗示机器人离线。纯诊断优化，一分钟内就能定位这类问题。

落地时顺带发现关联缺陷：safe_to_restart同样把解析失败归类为不可读应答，permits_restart却判定为允许重启，和注释描述完全相反。修复为SafeToRestart::Incompatible，参见#68。

场景2：robotctl与updaterd之间API_VERSION版本不一致

robotctl是指向current的软链接，跟随已安装版本；updaterd不会。一旦版本包修改API_VERSION，两者版本必然不一致，直到updaterd重启。而此时失效的命令恰好就是robotctl update apply——正是用来修复更新问题的命令。

普通操作即可复现，无需刻意构造：安装分支A，等待CI期间安装分支B；所有robotctl调用报错client speaks API v2, daemon speaks v3。解决办法：用版本匹配的robotctl二进制，或者手动重启updaterd；错误信息没有给出可行方案。

握手校验至少能捕获并打印双方版本，这点比场景1好。

最初提案：hello握手只在客户端版本高于守护进程时拒绝。该方案被否决（#77）：假设版本递增都是向后兼容，该假设不成立。v5新增pad.*属于兼容扩展；v4强制开启system.authenticate，属于破坏性变更。依靠常量无法追踪兼容性，仅凭版本号接受旧客户端，等于承诺向后兼容但没有强制保障机制。

最终方案：直接移除握手校验。拒绝逻辑的前提成立（版本号升级不代表兼容），但不能推出必须在握手阶段拦截。版本不匹配真正导致故障的场景：路由不存在或者参数结构变更。这两类场景会在调用时直接返回明确错误：Request::as_call返回METHOD_NOT_FOUND，参数解码返回INVALID_PARAMS。握手校验会在hello阶段拦截所有调用，只要版本号不同就全部拒绝，导致update apply、version命令同时失效。现在updaterd记录双方版本日志，正常处理请求；版本差异通过HelloResult::api_version返回给客户端，robotctl每次运行打印一行警告。

移除握手校验前必须满足两个前提，第二条是核心：

  1. 拒绝逻辑是冗余的，不只是烦人：robotd、configd、padd完全不校验版本号；updaterd在update.status查询前也不需要握手。duck-btctl在链路另一端也得出相同结论（#102）。
  2. 不能静默忽略未知参数：serde默认忽略未知字段，这也是握手校验看起来很必要的原因。v7新增ApplyOptions::from_dir，v6守护进程会忽略该参数，运维以为在本地侧加载目录，实际从配置源安装。现在所有参数结构体开启未知字段拒绝，返回INVALID_PARAMS并指明字段。仅向前校验：该规则之前编译的守护进程仍然会忽略未知字段，因此API_VERSION版本号升级仍然有意义。

提示文案重写，随校验逻辑一并删除。旧提示：client speaks API v2, daemon speaks v3，没有解决方案。现在修复方案放到robotctl警告信息，不会拒绝请求。

为什么这两类不属于安装流程漏洞

上面整套测试方案，都无法捕获这两个问题。两次事件制品包本身都正确；问题发生在更新之后，系统同时运行两套版本，这个状态只有更新后的机器才会出现。 第4项测试（本地真实systemd）如果容器同时部署旧版updaterd，可以捕获场景1带来的健康校验失败；但主动构造版本不一致场景属于另一类测试，更接近兼容性矩阵，应该单独维护，不属于安装测试。
